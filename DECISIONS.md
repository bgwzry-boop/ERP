## 2026-06-25 - Product Requirements Override Earlier Narrow V1 Plans

Early plans focused only on inventory, out/in stock, and finance. ## 2026-06-25 - Order Entry Should Start With Paste Recognition

Order entry should support a paste-to-parse dialog similar to express address recognition. Customer text should be parsed into size, color, quantity, print requirement, print content, and other order fields, then shown for human review. Multiple styles, colors, or print contents in one pasted message should be split into separate orders or sub-orders.

## 2026-06-25 - Enterprise WeChat Group Orders Are A Primary Input

Many customers place orders in Enterprise WeChat group chats. The order parser should handle copied group-chat text and extract customer name, fulfillment method, and latest delivery time when present, but missing fields should be judged by order type. For stock/common-goods orders, a clear customer/customer group, size/model, color, and quantity are enough to form a valid draft/order; missing fulfillment method or latest needed time is non-blocking pending confirmation, and the system can tell the customer the available stock and estimated ship-ready / pickup-ready time. If extended handle is not mentioned, default to normal handle; if style keywords such as 小熊, 喜, 福, or 覆膜 do not appear, default to plain/blank bags. For custom printed orders, missing print image, artwork/file, print content, print color, print position, or other production-critical print requirements should route to missing information. Missing latest shipment time on a custom order is a scheduling risk / pending confirmation, not necessarily an invalid order if production-critical information is complete. The business can gradually guide customers toward a more consistent order text format.

## 2026-06-26 - Every Worker Uses An Individual Account

Every person in the factory should use an individual account rather than shared person or machine accounts. Permissions vary by role, such as office staff, production supervisor, silk-screen worker, bag-making worker, packing worker, driver, and management. Operation records should default to the current logged-in account and should not be manually editable in normal workflow, including reporting, photos, packing, outbound, delivery confirmation, payment entry, price override, and review. Mobile screens should only show tasks and actions allowed by the current account's role and permissions.

## 2026-06-26 - Bag-Making Work Visibility Follows Machine Shift Schedule

Bag-making workers usually default to fixed machines, but the system should not hard-code a permanent machine-worker relationship because workers may rotate, change shifts, take leave, or temporarily cover another machine. V1 should keep scheduling lightweight: day-level schedule plus temporary substitution, without complex attendance shifts. Because the factory mainly runs a long day shift, the default can be one shift per day. Office staff or the production supervisor can update which worker operates each machine for the current day. A bag-making account can see a machine's work orders only when the current schedule assigns that account to the machine. Schedule records, actual operator, machine, reported quantity, photos, and timestamps should become the data foundation for later piece-rate / attendance / payroll calculation. V1 records only the foundation data; payroll calculation, morning/afternoon shifts, overtime, and leave-hour details remain later modules.

## 2026-06-26 - Silk-Screen Uses A Workshop Task Pool With Fixed Worker-Machine Defaults

The 4 silk-screen machines are generally bound to 4 fixed silk-screen workers, one worker per machine, but office scheduling should use a silk-screen task pool. Office staff assign same-day print orders to the silk-screen workshop / task pool instead of directly assigning each order to machine 1-4 or forcing a fixed sequence. The silk-screen workshop decides actual order and machine arrangement based on plate, print color, material availability, setup state, and delivery urgency. At the start of the workday, silk-screen workers can mark / claim orders from the task pool that they plan to print. A marked order is locked so other silk-screen workers cannot mark it again. Marking / claiming does not mean printing has started; it only means the worker is preparing to handle that order. The worker who marked it can cancel the mark, and office / supervisor can cancel it or assign the order to a specific worker. When the worker clicks `start printing`, the order enters `silk-screen in progress`, and the system records actual operator, actual machine from the worker's bound machine, and start time. The print photo must be uploaded after `start printing` and before `printing completed`; without it, the silk-screen worker cannot submit completion. In rare exceptions, office staff or the production supervisor can override / release the block from the backend, with reason, releaser, and release time recorded. When printing is completed, the worker submits actual printed quantity and finish time. The task pool can show suggested sequencing, but V1 should not force the workshop to follow it.

## 2026-06-25 - Stock Orders Should Auto-Check Inventory

Stock/common-goods orders are roughly 60% of current business. After order entry, the system should automatically check finished-goods inventory by size, color, warehouse/location, and available quantity. If stock is sufficient, the order follows the stock outbound flow. If insufficient, the system should generate or recommend a production work order. The system should also provide inventory warnings and replenishment suggestions by color and size.

For stock/common-goods order lines, V1 can automatically move to waiting for outbound only when parsing is clear, inventory is sufficient and trustworthy, pricing is complete, and there is no strong customer/order risk requiring manual handling. If fulfillment method or latest needed time is missing but the stock-core fields are clear, the line should move to fulfillment pending confirmation rather than missing information; it should not generate a concrete outbound / delivery task until the fulfillment method is confirmed. Ambiguous parsing, mainly workshop-reported / loose / unreviewed inventory, missing or failed price calculation, manual price override needs, strong customer risk, management-confirmation-required customers, abnormal notes, or missing production-critical fields on custom/scheduled-production/rush orders should keep the line pending office confirmation. Normal non-blocking risk hints do not stop automatic waiting-for-outbound.

Customer-group automatic recognition can show only a recognition-time inventory snapshot; it is not an inventory reservation. Order drafts do not reserve inventory, but should store the recognition-time available quantity, source, location, query time, and source confidence. When office staff creates a formal order, the system must re-check inventory and immediately reserve / lock it if still sufficient. A formal stock order in fulfillment pending confirmation should still reserve inventory once customer intent is clear, so goods are not taken by another order while delivery/pickup/needed time is being confirmed. Pending-fulfillment reservations should not auto-release after a timer; instead they enter a reminder list where staff chooses to keep holding, cancel, change quantity, or contact the customer. Initial reminder timing should be urgency-based: urgent/today/immediate/this-afternoon stock orders remind after 10 minutes, normal stock orders after 30 minutes, old-customer non-urgent orders that only miss pickup/delivery/express method after 2 hours, and unresolved items near closing enter an end-of-day pending list. Fulfillment pending confirmation should be a shared task pool, not individual assignment. The pool is visible to the two office clerks, the owner mother's / management mobile account, and production management / supervisor, while the two office clerks remain the primary operators. The system records the actual operator for each confirm/cancel/change/hold/contact action. Manual stock/common-goods order entry should offer two save actions: save and wait for outbound when fulfillment method, needed time, inventory, and price are clear, and save to fulfillment pending confirmation when fulfillment method or needed time is still unclear. The direct outbound save action re-checks and reserves inventory, creates the formal order, and records entry operator/action time/reservation result; the pending-confirmation save action creates the formal order, reserves inventory, and enters the shared pool without creating a concrete outbound / delivery task. Save and wait for outbound must not automatically print outbound/delivery/pickup notes; it only creates the waiting-for-outbound task and inventory reservation. Printing is a separate manual task action controlled by account permissions. V1 defaults to office staff as the only users with document printing permission; outbound workers, drivers, and workshop accounts are not default printers. First print and reprint both require print permission. Reprints should record reasons such as customer quantity change, damaged paper, lost document, information change, or other, with printer, print time, print count, electronic note number, paper note number, and reprint history retained. If inventory changed between recognition and review, the review screen should show the delta, such as recognized-time available 500 and current available 0, and route the line to shortage confirmation / customer decision rather than continuing to promise in-stock fulfillment. A final inventory check is still required before outbound.

When stock/common-goods inventory is insufficient, V1 should not automatically create production work orders. Stock/common-goods orders should check inventory per order line because customers often place many small stock lines together. Lines with stock can enter waiting for outbound, while lines without stock should wait for office / customer confirmation on whether the customer will wait. If the customer waits, create a shortage production / replenishment task linked to the original order line and prioritize the finished goods for that customer. The waiting line status should move from waiting for customer decision to wait, to waiting for replenishment / production, to scheduled, to production completed / waiting for outbound, to completed. Waiting for replenishment / production should show that the customer agreed to wait, the predicted lead time / estimated ship-ready date, and shortage quantity. If the customer does not wait, cancel / close that line while other available lines continue outbound. Printed custom orders do not use this stock-waiting logic because they are made to order. The system should show required quantity, available quantity, shortage quantity, inventory source / confidence, and predicted production lead time or estimated ship-ready date. V1 predicted lead time should be conservative and rule-based: use existing replenishment / machine plans when available, otherwise estimate from capable machines plus earliest schedulable date and expected production duration, add setup buffers for mold / handle changes or material waits, and fall back to estimated time pending confirmation when uncertain. Later versions should improve prediction from accumulated data such as historical production speed, actual machine capacity, mold-change duration, replenishment cycles, seasonality, and order completion records. It should generate copyable WeChat / Enterprise WeChat message text that office staff can edit before sending; V1 should not automatically send it to customers. After customer reply, office staff chooses all-to-production, ship inventory plus produce shortage, change accepted quantity, wait for unavailable lines, cancel unavailable lines, change quantity / color, or confirm later. When the customer changes quantity, color, or style because the original stock line is unavailable, the system should close / cancel the original unavailable line with a reason and create a new line that reruns parsing, inventory lookup, inventory reservation, price snapshot, and outbound / replenishment flow. The new line should default to the original customer order time and original fulfillment method, record the change time, require office confirmation for latest ship date, and use the price table version matched by the original customer order time. If the customer request is actually a later add-on, it should be treated as a new order / new line priced by the new customer order time. When the customer agrees to wait, the system should generate another copyable confirmation message explaining which lines ship first, which lines wait for replenishment / production, and the estimated ship-ready date; this also should not be sent automatically. Confirm later should create a follow-up reminder, defaulting to 2 hours but editable. If the latest delivery / pickup time is approaching or the customer keeps not replying, the system should strongly remind staff and recommend a phone call. Confirm-later records should store last contact time, next reminder time, responsible account, and notes. The system should not automatically split insufficient-stock orders without human confirmation.

If a customer changes quantity, color, or style because of unavailable stock and the newly created line is also unavailable, the system should return to the same waiting-for-customer-decision loop instead of creating a separate special flow. It should generate a new copyable customer message for the new unavailable line and retain the full change chain, including original line, new line, closure reason, customer confirmation record, change time, and current handling status.

When a customer confirms they will wait for an unavailable stock/common-goods line, the generated shortage production / replenishment task should split quantity into customer-locked quantity and opportunistic stock replenishment suggested quantity. Customer-locked quantity must be protected for the original customer. Opportunistic replenishment should be suggested from safety stock, target stock, recent sales, current scheduling, and matching production conditions such as size, color, and handle type, then confirmed or edited by office staff before entering the pending replenishment scheduling pool. If a customer order and stock replenishment can share the same production run, the system should recommend merged continuous production, but customer due dates and locked customer quantities remain the priority. Later predictions should improve with accumulated cycle-sales and seasonal demand data.

When actual qualified production differs from the planned quantity in a merged customer-waiting / stock-replenishment run, the system should allocate customer-locked quantities first and put only remaining qualified goods into stock inventory. For non-custom production such as blank stock/common goods and printed stock/common goods, the planned quantity is a target rather than an exact stop quantity. The factory often prefers to finish the roll because stopping halfway wastes changeover time and half-roll leftovers are hard to store, but finishing the roll is not mandatory. The system should recommend whether to finish the roll from backend data such as current inventory, target inventory, recent sales, cycle-sales patterns, expected inventory turnover time, warehouse pressure, waiting customer orders, later machine plans, and roll-change / mold-change / handle-change cost. After bag-size material-usage formulas and per-roll meters are available, replenishment suggestions should use size-based material usage plus per-roll meters to estimate one-roll output, approximate roll count needed, and whether finishing the roll is reasonable. Early V1 can default to a rough one-roll estimate using `1500 meters per roll`, without aiming for precision. Replenishment suggestions and push messages should show the rough calculation basis, including current inventory, target inventory, shortage quantity, default per-roll meters, rough one-roll output, recommended rolls / approximate pieces, expected inventory after replenishment, and recommendation reason. The result should be marked as a rough estimate, and office / scheduling staff must be able to edit the suggested production quantity. Finish-the-roll recommendations should not depend on manual tags such as common item, slow-moving item, or cautious replenishment. When V1 has limited data, it should make conservative recommendations from existing orders, current inventory, configured minimum / target stock, and short-term sales data, and show manual confirmation recommended when evidence is insufficient. If extra quantity is likely to sit in stock for a long time, or if inventory pressure is high, the size/color is slow-moving, or a more urgent machine task is coming, the system should recommend producing only the target quantity or a small overage instead of finishing the roll. If customer-locked quantity is satisfied, lower-than-planned stock replenishment should record target-stock shortfall and remain in later warning / replenishment logic, while higher-than-planned stock replenishment should enter stock inventory with an over-planned inbound quantity record. Plan-vs-actual differences should record reasons such as finish the roll, roll length difference, avoid half-roll waste, planned quantity entry variance, reported quantity variance, or other. If actual qualified quantity cannot cover customer-locked quantity, the system should mark a customer-locked quantity shortfall and strongly remind office staff / management to choose continuing production, customer-accepted short shipment, or changed due date / continued waiting. This is expected to be rare but is required as a control to prevent customer-locked goods from being mixed into normal stock.

When a stock/common-goods order line enters waiting for outbound or becomes a formal order in fulfillment pending confirmation, V1 should reserve / lock the matching inventory immediately. Inventory should distinguish on-hand, reserved, and available quantities, with available = on-hand - reserved. Reservations are per order line and release or adjust when the order is cancelled, rejected, quantity-changed, moved to all-production, manually released, or completed through outbound. Parsed previews alone should not reserve inventory.

Pending-confirmation stock/common-goods orders that are not yet formal orders should not reserve inventory by default. Office staff can explicitly use hold inventory when the customer asks to hold goods or a short hold is needed. Holds must have an expiry time; V1 can default to same-day 19:30 automatic release. Hold records should store holder, hold time, expiry, reason, order line, and reserved quantity, and expired holds should release inventory automatically unless the order moved to waiting for outbound, became a formal fulfillment-pending order, or the hold was extended.

If outbound staff finds that actual inventory is insufficient for a reserved stock/common-goods order, V1 must not silently mark outbound as completed. It should enter inventory variance handling, showing reserved quantity, actually found quantity, variance, inventory item, warehouse/location, and operator context. Handling options should include actual outbound plus shortage to production, actual outbound with customer-accepted short shipment, cancel this outbound and wait until replenished, or correct inventory quantity / inventory count adjustment. Variance records should link to the order line and inventory ledger for later inventory accuracy statistics. Normal outbound staff can initiate correct inventory quantity, but cannot directly change system inventory. The system should create inventory adjustment pending confirmation, and only office staff or accounts with inventory adjustment confirmation permission can confirm it. Confirmation records should store initiator, confirmer, time, before/after quantity, variance, reason, linked order line, and notes. Inventory adjustment reasons should use fixed options plus optional notes; V1 fixed options should include wrong location searched, inventory count shortage, inventory count overage, outbound not recorded, inbound / workshop report quantity inaccurate, damaged / polluted / unsellable, workshop-reported inventory variance, historical inventory inaccurate, and other. Inventory adjustment pending confirmation belongs in the approval queue. Small quantity / low amount adjustments should enter the list without immediate push; large quantity or high estimated amount adjustments should immediately push to accounts with inventory adjustment confirmation permission. Push thresholds should be configurable by quantity variance and estimated amount. All inventory adjustments must retain records for later variance statistics by size, color, location, worker, and inventory source. Inventory adjustment only corrects inventory book quantity and must not directly advance the customer order status; order progress is determined by the selected variance handling result, such as actual outbound, shortage production, customer-accepted short shipment, or waiting until replenished. For actual outbound plus shortage to production, the internal order should show original ordered quantity, delivered quantity, pending delivery quantity, and shortage production / replenishment status; only actually delivered quantities should enter customer reconciliation by delivery date, and undelivered shortage must not be billed early. For customer-accepted short shipment, the order must keep original ordered quantity and actual outbound / shipped quantity separately. Order status should indicate short shipment confirmed rather than plain completed. Outbound, delivery, inventory deduction, and reconciliation quantities should use actual delivered quantity, while notes preserve the original ordered quantity and customer confirmation. Customer-accepted short shipment requires a lightweight confirmation record with confirmation method and content; screenshot/evidence photo and notes are optional, and the system records entry operator and time. If the goods were merely in another location or the adjustment is invalid, office staff can reject the pending adjustment and choose another handling path.

## 2026-06-25 - Inventory Warning Uses Hybrid Safety Stock And Demand Signals

Inventory warnings should combine manually configured minimum/target stock per size + color with dynamic suggestions from recent 7/15/30 day sales. V1 should generate replenishment suggestions for office confirmation rather than automatically creating production work orders. Replenishment reminders should be tiered: order-entry shortages appear first as desktop in-page reminders because office clerks enter orders on computers; a fixed daily replenishment summary can push to office / scheduling staff around 4 PM; and severe shortages or risks to already-promised customer due dates should immediately strong-remind relevant permission-based recipients. Normal replenishment suggestions can be confirmed collaboratively by office clerks and the production supervisor because they work together and can communicate offline easily; the system should not turn normal replenishment into a heavy approval workflow. Clearly large replenishment quantities, long estimated turnover, long-lived overstock risk, or suggestions that may consume machine time needed for promised customer orders should enter boss review / management watch as a non-blocking reminder. Recipients should be configured by account permissions, not hard-coded person names. Customer purchase history and seasonal cycles should later improve demand forecasting and reduce inventory pressure.

## 2026-06-25 - Confirmed Replenishment Enters A Scheduling Pool

Confirmed stock replenishment suggestions should enter a pending replenishment scheduling pool, not immediately become fixed production work orders. Confirming replenishment and formally scheduling a machine are separate steps: confirmation only accepts the replenishment need into the pool, while formal scheduling happens when the production supervisor or another account with scheduling permission assigns the task to a specific bag-making machine, date, and sequence. If the machine is not yet known, the task should remain in the pool. After a replenishment task is formally scheduled, the production supervisor or office staff may still adjust sequence for urgent customer orders or shop-floor conditions. Normal replenishment defaults below already-promised customer orders, but changes must keep audit records with operator, time, original/new machine and sequence, and reason. If the task includes customer-locked quantity, the system should check whether moving it back risks the promised customer due date, strongly remind staff, and require a confirmation reason. The scheduler should match replenishment tasks with customer orders by size, color, handle/strap setup, and timing so stock replenishment can run continuously after compatible customer orders and reduce changeovers, waste, and setup time.

## 2026-06-25 - Do Not Require Product Use Category For Order Entry

Bag handle material, width, and gram weight are fixed. The only handle variation is normal/default length versus extended handle. Customers generally do not state product use/category when ordering, so V1 should not require a category such as advertising bag or clothing-store bag. Order entry should parse model/size, color, quantity, and handle type. If extended handle is not mentioned, default to normal/default handle; if extended handle is explicitly mentioned, use extended handle. Handle type affects price and batching/continuous-production matching.

## 2026-06-25 - Model And Size Are The Same For Current Orders

For current business, customer-spoken model and size are the same concept, but some common names are aliases rather than physical measurements. `30*38`, `30*38*10`, `30*37`, and `30*37*10` refer to the same common spec group. Actual size format is `width*height*gusset`; the actual production, inventory, and costing standard is `30*37*10`, meaning width 30cm, height 37cm, and bottom/side gusset 10cm. Customer-facing UI and historical documents can preserve the `30*38` wording, but normalized spec, inventory matching, scheduling, material usage, and costing should use `30*37*10`. Current business does not include no-gusset bags.

## 2026-06-25 - Size Parsing Needs Alias Mapping

Customers express sizes inconsistently: full specs, shorthand specs, horizontal/vertical wording, or labels such as small, medium, large, and extra large. The order parser should use a size/spec alias table. V1 can use global aliases, then add customer-specific aliases when different customers use the same label for different actual sizes. Ambiguous parses should require office confirmation.

## 2026-06-27 - Similar Color Or Size Is Only A Hint, Not Inventory Availability

Stock/common-goods inventory matching must be exact on size/model, factory standard color, handle type, and finished-goods style before the system treats an item as in stock. Color aliases map different wordings to the same standard color, while size aliases parse customer wording; neither should be treated as automatic substitution. V1 may show possibly similar inventory as a reference for office staff, but similar color/size hints must not count as available inventory, reserve stock, move an order line to waiting for outbound, or generate customer copy promising in-stock fulfillment. Because most customers place orders after receiving e-commerce orders from their own buyers, color and size usually cannot be changed. Only explicit customer/office confirmation to change color, size, or style should close the original unavailable line and create a new line that reruns inventory and pricing. V1 does not distinguish color differences between batches under the same factory standard color; batches and inbound times should be retained for traceability, FIFO reference, stocktaking, and exception investigation, but not used to block same-standard-color stock matching or require same-batch outbound.

Finished-goods inventory should support practical warehouse zones. Plain stock/common goods are generally stored together and arranged by model/size, while printed stock/common goods are stored separately. V1 location data should stay lightweight and include zone/area type, model/size group, color or finished-goods style, and notes; it should not require shelf number, layer number, or bin/cell number. Example locations can be plain stock area / 30*38 / near red, printed stock area / bear / 25*23, or waiting-pickup area / customer tail number. Shelf/layer/bin or QR-coded location labels can be added later after warehouse organization stabilizes. FIFO can be used as the system's recommended deduction order when multiple batches/locations exist, but it must not be forced; outbound completion records the actual location, quantity, operator, and time, and actual outbound records override the recommendation without being treated as an exception.

## 2026-06-25 - Price And Size Table Captured

The current price/size table image was saved as `docs/product/assets/price-size-table-2026-04-19.png` and extracted into `docs/product/requirements.zh-CN.md`. Vertical size classes start with `25*32`, `30*38 / 30*37`, and `35*41`; horizontal size classes start with `35*27`, `40*30 / 40*32`, `45*37`, and `50*40`, with `40*30` and `40*32` both treated as horizontal medium. Exact size is still retained for inventory, pricing, and production.

## 2026-06-25 - Printed Stock Styles Are Separate From Custom Print Content

`小熊`, `喜`, and `福` are printed stock/common-goods bag styles, while `覆膜` is another product category that is currently rarely produced. These styles use normal/default handle length and should be recognized as finished-goods styles or process types rather than ordinary colors/sizes or custom print content.

## 2026-06-25 - Stock Finished Goods Inventory Dimensions

Stock/common-goods finished inventory should be separated by size, color, handle type, finished-goods style, and warehouse/location. Finished-goods style includes at least plain/blank, `小熊`, `喜`, `福`, and `覆膜`. Finished-goods style must also validate allowed size ranges; for example, 小熊 has no `30*38` size, so the system must not generate `30*38 小熊袋`.

## 2026-06-25 - Finished Goods Inventory Unit Is Pieces

Finished-goods inventory uses pieces as the primary unit. The Chinese UI can display either `个` or `只`, but internal storage should normalize to `个`. Packages, bundles, and boxes belong to packing/outbound details, not the primary inventory unit.

## 2026-06-25 - Finished Goods Inbound Counting Is Scenario-Based

Printed custom orders and printed stock styles usually go through packing, so packing workers can count and confirm final quantities. Blank stock bags often remain loose and should not require mandatory packing or outbound-staff counting before inventory. V1 should allow bag-making workers to report completion quantity into workshop-reported/loose stock inventory, with later outbound, spot count, or inventory count adjustments when differences are found. Exception cases can require review.

## 2026-06-25 - Support Machine-Side Direct Outbound

Blank stock bags may be dispatched directly from the bag-making machine, especially in busy seasons when customers or pickup staff wait beside the machine. The target process is to train customers to place orders in WeChat / Enterprise WeChat groups in advance, with office staff entering the order and warehouse outbound staff preparing goods, performing outbound, and confirming actual taken quantity. Old customers directly entering the bag-making workshop and later reporting quantity should remain a transition-period exception, not the main flow. The system should support machine-side direct outbound by recording production completion and outbound/fulfillment in one linked flow, with machine, operator, confirmer, quantity, fulfillment method, and inventory movement source retained. Machine-side direct outbound must link to a customer and formal order/order line; if no ERP order exists yet, office staff should create a quick stock/common-goods order before completing the outbound. Warehouse outbound staff are the default priority confirmer; if they are not on site, production supervisor or office staff can proxy-enter the confirmation as pending warehouse review. Bag-making workers report production quantity only and should not be the default final confirmer of how many pieces the customer actually took. Customer self-reported quantity is a reference only and should not directly deduct inventory until warehouse / office confirms it. The flow may use electronic confirmation first when the site is busy, with office staff later back-printing or linking the paper outbound/pickup document. The shortest busy-season flow is select customer/order, enter taken quantity, choose machine-side pickup / machine-side direct dispatch, and complete; notes, paper documents, and review can be backfilled. A same-day machine-side direct outbound pending-review list should prevent missed records; unreviewed items after the day ends get a red-dot reminder, and items older than one day enter follow-up. Confirmed machine-side direct outbound should immediately offset that day's workshop-reported / machine-side output. For cross-day tasks, machine-side direct outbound may happen before final report completed quantity; the dispatched quantity should link to that day's output record and the corresponding order / customer, while remaining unshipped quantity stays as task progress and does not become normal available inventory. When the task is finally completed, quantities already dispatched machine-side must be deducted before moving remaining qualified goods to packing, customer-locked allocation, or stock inventory, avoiding duplicate inbound or delivery. Variances are handled through inventory adjustment / cycle-count correction. If a variance can be linked to an order, machine, operator, or outbound confirmer, the system may create a responsibility clue, but it must never auto-deduct pay.

## 2026-06-25 - Workshop-Reported Loose Inventory Is A Labeled State

For blank stock bags, `workshop-reported inventory` and `loose stock inventory` are not conflicting buckets. They describe source/confidence and packaging state: workshop-reported, loose, and unreviewed. This inventory can be shown as available, but must be labeled separately from counted warehouse inventory. Outbound, spot count, or inventory count can later confirm or adjust it.

## 2026-06-25 - Bag-Making Reporting Uses Piece Count With Bundle Support

Bag-making workers receive assigned tasks on the workshop mobile side, submit completion reporting, and then continue to the next task. The mobile task list should distinguish customer orders, replenishment, replenishment with customer-locked quantity, and custom printed orders while keeping the list compact. The list should show scan-friendly fields such as task type, size, color, handle type, planned / target quantity, machine, sequence, rush flag, and latest completion / shipping time. Customer orders and custom printed orders show the customer name; pure stock replenishment does not; replenishment with customer-locked quantity shows the locked customer and locked quantity. Custom printed orders may show only a summary in the list, with full customer, order line, print content, notes, photo requirements, exception records, and process quantities available after opening the task. Task-detail actions vary by type: customer / custom printed orders support start bag-making, upload finished-goods photo, report completed quantity, and report exception; pure stock replenishment supports start production, report completed quantity, and report exception without requiring a finished-goods photo by default; replenishment with customer-locked quantity follows stock replenishment actions, then allocates customer-locked quantity first after completion reporting. Machine breakdown, repair waiting, printing problems, and similar exceptions use report exception or supervisor / office backend records instead of mandatory detailed downtime tracking. The primary submitted and saved quantity should be piece count because partial bundles and tail quantities are common. One bundle usually equals 50 bags, so the UI can support bundle count plus loose pieces as an auxiliary input and convert that to pieces. The reporting form should use prefill + editable from the planned/order quantity. Workers can change the prefilled value before submitting the actual completed piece count. The system should record the final piece count and retain the prefilled value, submitted value, modified flag, quantity source, and modification reason/note. To reduce lazy default confirmation, reports also retain prefill source and unchanged-default submission state. Later packing, outbound, spot count, and inventory-count differences should feed worker/machine reporting quality metrics and exception sampling.

After customer shipment-preparation notification, customers may rarely call to change packing requirements, such as from 1000 pieces per package to 500 pieces per package. ## 2026-06-26 - Printed Quantity Tolerance Tracks Silk-Screen Overprint And Process Loss

## 2026-06-26 - Raw Material Usage Will Feed Future Gross Profit

Fabric and handle raw-material purchasing is confirmed to be primarily priced by kg/weight, with supplier delivery notes recording supplier, document date/number, goods name/color, specification model such as width/GSM/meters, piece/roll count, total kg, yuan/kg unit price, line amount, and per-piece/per-roll weights. Normal/default body GSM is 78g; normal/default handle length is 38cm, handle raw-material width is 5cm, handle GSM is 60g, and each bag has 2 handles unless a special order or actual batch overrides those defaults. The factory currently has 3 fabric suppliers with different prices, and handle prices also vary by supplier, so body fabric supplier/batch and handle supplier/batch must be stored separately in cost snapshots. Main fabric widths are usually two-digit centimeter widths, so specification parsing and labels must distinguish handle material from main fabric material. Raw-material purchase cost excludes freight; freight should be tracked separately if needed, not allocated into the raw-material cost snapshot. Raw-material labels should not show purchase price, amount, or supplier arrears by default; cost data belongs in permission-controlled backend views. ## 2026-06-27 - QR And Barcode Labels Start With Goods Cards And Raw Materials

QR/barcode labels should start with practical batch-level objects instead of individual bags. The first outbound use case is goods cards for prepared goods, waiting pickup / express areas, packages, pallets, baskets, or temporary preparation areas. Scanning should open or validate the outbound task / package and warn if it does not match the current customer or document, but V1 should not make scanning mandatory for every outbound action. Labels must include human-readable fields so the factory can continue working if a scanner, phone, or label is unavailable. The encoded QR/barcode value should preferably be only an internal system ID, such as preparation task ID, outbound note number, package ID, or raw-material batch / roll number, not a full copy of mutable business details. QR/barcode goods-card and raw-material label printing should follow document-printing permissions in V1: office staff or accounts with print permission print/reprint labels, while warehouse/outbound staff attach labels, scan, check, and use them. Warehouse label-printer permission can be opened later after the process is stable. Raw-material arrival should be handled by office staff or a designated person checking the supplier delivery note against physical material fields such as meters, GSM/fabric weight, total kg, color, width, supplier, and roll/batch count. Photo recognition/OCR can prefill inbound drafts and cost snapshots, but it cannot directly create usable inventory; an authorized human must verify and confirm before official raw-material batch/roll numbers and labels are generated. After labels are printed and attached, scanning confirms labeled inbound and records operator, time, and location. If delivery note, OCR result, and physical material disagree, the material enters inbound exception / pending confirmation instead of available inventory. For raw materials, fabric rolls should preferably use one label per roll; handles should also be labeled by roll/piece when they arrive by roll or piece; ink and auxiliary materials can be labeled by barrel, box, package, or batch. Raw-material inventory needs its own ledger: inbound, material issue/outbound to production, return/leftover registration, and stock adjustment. Scanning a raw-material label alone must not automatically deduct inventory; scanner/phone use must be in material issue/outbound mode, or a production task, material issue document, or machine issue page must be selected first. The recommended flow is scanning/selecting the production task or machine/purpose first, then scanning the raw-material roll/batch, validating matching fields, defaulting to full-roll issue where appropriate, and confirming. Leftover registration should record remaining meters/weight, location, status, and reusable specification. Raw-material inbound, issue/outbound, and leftover records should later link to production tasks for material-consumption and gross-profit data. V1.5/V2 can support both 2D scanners and mobile scanning, with scanner input treated as keyboard-entered internal IDs where possible.

## 2026-06-26 - Customer Risk Hints Do Not Block Order Entry

Strong hints cover cases such as debt above threshold, overdue debt, high recent complaint count, or large after-sales / compensation amount. ## 2026-06-26 - Review Items And Approval Items Are Separate

V1 should separate non-blocking `review / watch` items from blocking `approval` items. Review / watch items are reminders, such as customer debt above threshold, overdue debt, strong customer risk hints, large rounding / write-off, large after-sales compensation or allowance, current-order manual price override above threshold, or abnormal discount / allowance above threshold. They should not block order entry, scheduling, production, outbound, delivery, statement generation, or payment recording by default.

Approval items require authorized confirmation before the related item can take effect, such as price-table version review before publishing / becoming effective, or performance / deduction confirmation. Approval should only block the related item itself. For example, an unapproved new price version cannot become effective, but existing-price orders can still continue through production and delivery. An unconfirmed performance / deduction result cannot enter payroll settlement, but after-sales supplemental shipment, exchange, or customer reconciliation can continue.

When multiple authorized accounts receive the same approval item, V1 should treat the first valid handling result as final and should not require multi-approver signoff. If one authorized person confirms, returns, or otherwise completes the item, other recipients should see who handled it, when, and with what result, and they should not be able to repeat the action. If two people submit almost simultaneously, only the first valid submission is accepted.

Approval items should be actively pushed to mobile accounts with the matching approval permission. Review / watch items should default to the list plus a daily summary, and only severe cases should immediately push, such as customer debt over 20,000 CNY, long-overdue debt, or very large after-sales compensation / allowance. Customer notes come from the customer order or follow-up requirements; office notes are internal-only notes for office additions, temporary communication, and operational reminders. Outbound worker mobile keeps only three primary actions: complete outbound, quantity mismatch, and unable to outbound. Mismatch and unable-to-outbound records should later feed inventory accuracy, warehouse/location cleanup, and advance-picking quality metrics. ## 2026-06-27 - Complete Outbound Quantity Defaults To Expected Quantity

On normal complete outbound, actual outbound quantity defaults to the expected / reserved quantity, so outbound staff do not need to re-enter quantity for normal orders. This keeps original ordered quantity, actual delivered quantity, and reconciliation quantity from becoming ambiguous.

## 2026-06-27 - Changed Outbound Documents Must Be Reprinted

After an outbound note, delivery note, or pickup record has been printed, any change to order quantity, actual outbound quantity, fulfillment method, price, customer information, or key notes must void the old document and require a revised electronic document plus a newly printed paper document. Handwritten quantity changes on the old paper document are not accepted as the formal fulfillment or statement basis. The main real-world case is factory self-pickup: after the order is entered, warehouse picking may find insufficient goods, the outbound worker contacts the office in person or by phone, and the office negotiates with the customer to change quantity, wait for replenishment, or cancel the shortage. If the customer accepts a changed quantity, such as original order 500 and actual outbound 430, the office changes the order, prints a new 430-piece pickup / outbound note, and marks the original 500-piece note voided. Delivery should normally hand the driver packed goods plus the matching document; the driver checks before loading but does not change the order or document. If delivery goods/packages do not match the document before loading, the flow returns to warehouse / office handling and a new delivery note is printed if needed before the driver leaves. The voided document is retained only for traceability, while the new document is used for customer signature, driver handoff where applicable, customer statement, and payment collection. Voiding old documents, generating revised documents, and reprinting new formal documents are office-side / document-printing-permission actions only. Outbound workers, drivers, and workshop accounts cannot directly void or reprint formal documents. Reprint history should record old/new note numbers, key before/after differences, void reason, operator, time, and print count.

## 2026-06-27 - Self-Pickup Quantity Change Confirmation Is Lightweight

For example, 500 ordered versus 430 actual at 0.36 RMB only differs by 25.2 RMB and can use simple on-site verbal confirmation for an ordinary customer; 5000 ordered with 800 short, or a variance worth several hundred RMB, should require notes or WeChat evidence.

## 2026-06-27 - Self-Pickup Quantity Shortage Has Three Outcomes

When factory self-pickup finds insufficient quantity, office exception handling should offer three explicit outcomes. First, customer accepts short shipment and cancels the remainder: ship, deduct inventory, reprint documents, and reconcile only the actual quantity, while the remainder is cancelled. Second, customer takes the actual quantity now and waits for the remainder: keep original ordered quantity, ship and reconcile the current actual quantity only, and move the remainder to waiting for replenishment / waiting for outbound, with a later outbound / pickup note when replenished. Third, customer does not pick up now and waits until full quantity is ready: current outbound is not completed, no current outbound quantity is deducted, nothing enters the statement yet, and the order remains waiting for replenishment / waiting for outbound. All outcomes must retain original ordered quantity, on-site actual quantity, variance quantity, customer confirmation method, operator, and timestamp so order details, documents, inventory ledger, and statements remain clear.

## 2026-06-27 - Self-Pickup Remainder Uses Original Price Snapshot

## 2026-06-27 - Self-Pickup Remainder Needs Follow-Up But No Auto-Cancel
