## Runtime And Security
- Runtime mode is explicit. Production fails closed unless PostgreSQL, object storage, strict authentication, and audited secure env inputs are active. Formal login, startup restoration, session revalidation, and password change are transport-only candidates; the active action accepts and persists only its current result, whose runtime session, user identity, and core permissions must be complete, so stale or malformed responses cannot overwrite or clear a newer browser session. A malformed 2xx session revalidation is an explicit local invalidation that clears the tab and returns to login; only network/5xx failures remain retryable. A password-change success may restore permissions only while the original runtime tab token remains current; logout, revoke, expiry, or a newer login discards the response without a success claim. Runtime restoration also requires the server's explicit `authenticated: true`, even when its session and permissions otherwise look complete.
- Request bodies cannot choose authenticated identity. Permissions use one shared role catalog and account-specific extensions.
- Sensitive env values, paths, URLs, tokens, commands, and evidence outputs remain redacted and outside Git. Public `/api/health` is built from a fixed allowlist: repository/storage adapter kinds, runtime safeguards, production-env application state, and persistence-profile summaries are normalized; unknown extensions are dropped and free text is sanitized before exposure.
- Production writes require durable idempotency/revision checks and transaction-backed repositories. A business decision is an immutable direct/delegated record whose decision-maker, channel, decision time, content, and authorization evidence are distinct from the server-authenticated operator and entry time; purchasing, scheduling, fulfillment variance, and statement variance/write-off commands persist it atomically. Every A/B-editable write uses `expectedRevision` and returns the authoritative revision on conflict. Paper outbound instructions and carrier labels are different documents and print jobs, and publishing a production schedule atomically creates its formal schedule record rather than relying on a synthetic read projection.
- Operational navigation actions are reference-driven: a todo opens its persisted draft, inventory item, fulfillment, or statement when resolvable; preview actions reuse the real preview contract, and unsupported actions fail visibly without synthetic success messages.
- Todo reference health is server-authoritative and projected as `valid`, `missing`, or `unverifiable`. A missing target blocks navigation/printing and remains visible for office review; unverifiable external references cannot be silently treated as valid.
- An unhandled todo with a missing or unverifiable reference may be manually relinked by an authenticated office operator. The server requires a reason, validates the target, and atomically records the changed reference, event, operation log, operator, and before/after evidence; handled todos, valid references, and invalid targets are rejected.
- Todo relinking is semantically type-safe. The server owns the allowed reference types for each todo category, candidate projection and UI controls reuse that allowlist, and an existing target of an incompatible type is rejected before lookup/persistence. Visible operational labels use Chinese text instead of internal enum values.
- New todo creation uses the same server-owned resolver and semantic allowlist before its surrounding transaction starts. Packing completion writes the next-step todo and event in the same transaction; a legacy production line without fulfillment receives an order-line-linked remediation todo and cannot be presented as ready for trusted label printing.
- A missing fulfillment created by a historical packing chain is repaired only through one authenticated, idempotent, server-authoritative transaction. The command requires the exact open remediation todo, a real express/LTL order line, one completed packing task, unbound package details whose sum equals actual packed quantity, and no existing fulfillment; it atomically creates the fulfillment, binds packages, closes the remediation, creates the fulfillment-linked label todo/events, and writes the operation log. Generic todo handling cannot close this remediation.
- Default demo data must satisfy the same server-authoritative todo-reference and semantic-type contracts as normal writes. Broken legacy references are isolated test fixtures, not default operational data; synthetic order-draft fallback is allowed only for non-production local-memory cold starts and never overrides a production or PostgreSQL empty state. Real-sample seeds are separate private demo/test inputs: they must retain 20-50 confirmed anonymized source-message cases, all required V1 scenario coverage, private file permission, and no direct identifiers; a no-overwrite private empty template requires explicit creation confirmation, and its offline precheck exposes only redacted aggregates without starting API or printing input paths/content. Absent, unsafe, incomplete, or production-mode input fails closed and never substitutes for formal production data.
- Todo reminder/SLA state is server-authoritative. The API persists creation timestamps for new todos, computes waiting minutes, 30-minute red dots, one-day follow-up, same-day pinning and active/expired snoozes from one policy, and sorts the full filtered set before pagination. The client may parse legacy display strings only for local fallback data.
- Local/demo todo persistence must preserve the same observable write guarantees as PostgreSQL: reads return versioned snapshots, identical idempotency requests replay without duplicate events/logs, changed payload reuse conflicts, and a stale concurrent action fails with `409 BUSINESS_WRITE_CONFLICT` before mutation. PostgreSQL evidence must use strict authentication and two formal role sessions, not seed headers alone.
- Production todo capacity evidence uses an explicitly confirmed, hard-bounded, GET-only runner against an existing `/api` target. It requires a server-verified formal runtime session, rejects seed/legacy identity, stores no response payloads or todo identities, reports P50/P95/error rate plus server sort/reminder contracts, and cannot count as production evidence until it is run against the real long-running production API.

First-stage orchestration only consumes an independently generated report and never initiates load without the runner's explicit confirmation; handoff packaging and the go-live status API/UI independently recheck and expose only an allowlisted snapshot, while the browser remains unable to initiate production load.
