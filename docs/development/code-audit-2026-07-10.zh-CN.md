## 发现与修改建议

### P0：Git 本地基线已固化，尚缺远端备份

审计后已将运行/数据层、前端领域、文档和 CI 共 `367` 个文件分组复核，`server/`、`scripts/`、`db/` 和多个 `src/` 目录均纳入本地提交 `72f25c4`。运行产物和真实环境文件仍由 `.gitignore` 排除，差异格式检查、依赖安装与审计、全量测试和 OpenAPI 校验通过。当前仓库未配置 Git 远端，因此只能证明本机可按提交回滚，不能据此认为代码已有本机外备份或发布基线已可从远端恢复。

修改方式：由仓库负责人提供受控 Git 远端地址和访问权限，将 `codex/p0-office-hardening` 推送后，在新的空目录执行 clone、`npm ci`、`npm test` 和 OpenAPI 校验。后续提交继续按业务主题审阅，不得通过无差别 `git add -A` 混入运行产物、真实配置或现场证据。

### P0：真实 PostgreSQL 集成尚未复跑

已识别的 29 个高风险仓储均已从 `spawnSync("psql")` 迁移至 `server/postgresPoolClient.mjs`。附件元数据、打印设备、打印作业和打印设备现场测试在启动期异步加载到 workspace；打印就绪聚合只读取该投影，写入和 API 列表读取均等待连接池结果。这样消除了 Node 事件循环阻塞和连接串进入子进程参数的风险。

本轮已实际尝试执行 `npm run db:postgres-live:check`，但审计环境没有 Docker，检查在启动容器前被 `Docker is required` 阻断。现有回归覆盖了 repository 注入边界、连接池事务、API、打印作业队列、现场 QA、OpenAPI 和构建，但不能替代真实数据库约束、索引、事务隔离和多进程并发验证。

修改方式：在可用 Docker 或隔离测试 PostgreSQL 中执行 `npm run db:postgres-live:check`，确认 29 个仓储及 API 路由的真实表约束、事务、读写一致性。通过前不得把这项迁移当作生产数据库验收完成。

### P0：前端业务写客户端已完成严格模式收口

审查到的业务写客户端均已采用 `isOfficeApiServerRequired(options)`：严格模式下捕获网络异常会返回 `api_error / blocked`，不会产生本地业务投影。只读列表可保留降级，但必须在界面标明数据来源和失效状态。V1 状态页的 live action 降级路径原本即包含 `blocked=true`，不会显示为已执行。

### 已修复：legacy SQL 字符串构造

主数据复核/导入、生产排产/打包、原材料入库/供应商月结在本轮完成 `{ text, values }` 迁移后，静态扫描在 PostgreSQL 仓储中不再发现 `sqlLiteral(...)`。所有已识别仓储通过 `postgresPoolClient` 直接将 values 传给 `pg`；专项检查覆盖 SQL 结构、values 与单引号业务文本不进入 SQL。剩余风险是缺少真实 PostgreSQL live 验证，而非遗留字符串构造。

### P1：核心文件过大，职责混杂

- `server/apiServer.mjs` 为 23,426 行；认证、附件、订单、生产 / 打包、库存物料 / 流水 / 修正草稿、交付列表 / 详情、对账客户 / 单据详情、公共待办、打印批次 / 设备 / 作业、原材料入库 / 供应商复核、主数据和系统读取路由已分别拆到 `server/routes/`；附件、待办、完整打印、库存修正创建 / 确认 / 占用释放、订单、交付、对账、生产 / 打包、原材料、司机、主数据及 21 个系统预检 / 受控执行动作的写入分发也已拆出，且已删除相应不可达旧读模型。多数业务实现仍在主文件。ESLint 当前为 0 错误 / 0 警告。
- `src/pages/office/index.jsx` 约 13,148 行。
- `src/App.jsx` 约 10,822 行。
- `src/services/officeV1GoLiveStatusApiClient.js` 约 5,540 行。

修改方式：先不重写。按路由 / 领域渐进拆分：API 继续拆为 auth、inventory correction、fulfillment、statements、production writes、operations 路由模块；前端将页面事件处理移入按领域划分的 hooks / reducer；状态页的上线动作拆成 environment、evidence、release 三个客户端。每次只拆一个路由或页面并保留原有回归脚本。

### 已修复：API 客户端重复请求和鉴权代码

审计时有 16 个客户端各自实现 `request*Api`、`build*ApiHeaders`、JSON 解析和错误映射，严格模式判断也因此分散，容易继续漏改。已新增 `officeApiClientCore.js` 并迁移库存、主数据导入、生产 / 打包、打印、订单、交付、待办、对账、原材料、附件、司机 / 移动端和 V1 状态客户端；静态扫描现有独立 `request*Api` 封装为 `0`。共用核心只负责传输 / 鉴权 / 标准错误，业务 URL、payload、响应映射、附件 URL 处理与本地降级仍由领域客户端控制。

后续规则：新客户端必须直接使用 `requestOfficeApi`；只在领域模块保留业务响应、下载 / blob、附件 URL、设备桥接和降级策略。每次新增特殊传输协议时先扩展并测试核心，而不是复制新的 request / header helper。

### 已修复：事务仓储重复的 `queryJson` 适配层

订单确认、出库/交付和完整对账域原先分别复制连接池创建、`queryJson` 测试注入和 `transactionJson` 适配。现已统一到 `server/postgresTransactionExecutor.mjs`，五个领域仓储只保留各自 SQL、结果标准化和 workspace 投影；现有五条事务专项回归全部通过。

后续规则：新的参数化事务优先复用 `createPostgresTransactionExecutor(options)`。该工具不能吸收领域 SQL、结果标准化或 workspace 投影，避免形成一个巨型通用仓储。

### P1：测试治理缺口

当前有大量 `scripts/check-*.mjs` 专项脚本，`npm run lint`、`npm run check:core` / `npm test` 已聚合静态检查、API 结构 / 安全 / 启动、全部前端 API client、数据层仓储和构建。`.github/workflows/ci.yml` 在 push / pull request 以只读权限执行 `npm ci && npm test`。ESLint 当前为 `0` 错误 / `0` 警告；仍没有 `npm run typecheck`、格式化强制、TypeScript 或浏览器端到端测试配置。

修改方式：将 lint 警告按领域分批清理，再补类型检查和格式化；复杂流程随后补 Playwright 冒烟：登录、订单确认、出库、收款、司机送达四条主线即可，避免一开始做大而脆弱的全量 E2E。

### 已修复：V1 状态页离线备用数据误报

`src/pages/office/index.jsx` 在 API 状态未读取成功时不再显示硬编码日期、完成度或发布门禁。页面显示“状态未读取”并抑制固定数字；最近成功后端快照保留时间戳，超过 15 分钟会标记为过期，短暂 API 失败会标明最近快照。残余风险是页面仍依赖后端状态产物本身的正确性，且当前生产环境、真实数据库、对象存储、打印、司机真机、现场证据和签字尚未完成。

### 已修复：前端 seed 账号口令

`src/services/officeAuthService.js` 原先内置 prototype seed 用户名和密码，生产构建会包含这些演示口令。现在浏览器不再持有该凭据表；它只向 `/api/auth/prototype-login` 提交用户 ID。端点仅可在非严格本地原型模式创建 seed 会话，严格认证始终返回 `AUTH_SEED_LOGIN_DISABLED`。生产构建扫描确认所有 seed password 均不在 `dist`。

仍需改进：这只消除了前端口令暴露面；正式身份仍应使用已部署的服务端账户、密码哈希、撤销和会话管理，而不是原型 seed 用户。
