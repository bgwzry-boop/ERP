# ERP 系统整改执行方案

制定日期：2026-07-11
版本：V4
适用范围：V1 生产就绪、代码精简与 UI 收口

## 一、当前结论

当前系统是高完成度 ERP 原型和 V1 候选实现，但还不能宣布生产上线完成。

| 指标 | 当前值 | 说明 |
| --- | --- | --- |
| P0 可演示原型 | 约 `97-98%` | 办公室主流程、API 边界和大部分异常入口已具备。 |
| V1 真实上线就绪 | 约 `80-83%` | 生产事实源、真实基础设施、设备和现场验收仍未闭环。 |
| 发布门禁 | `0/4` | 未达到正式发布条件。 |
| 现场证据 | `0/34` | 自动化报告不能代替现场证据。 |
| 负责人签字 | `0/6` | 办公室、库房、车间、司机、财务、管理尚未签收。 |

已完成批次 A，以及批次 B 的 B1-B2：

- `demo/test/production` 运行模式和权限隔离已建立。
- production 强制严格认证、PostgreSQL、对象存储和 `Idempotency-Key`。
- 订单、库存、交付、对账、原材料、打印和司机核心写链已有首轮事务、幂等和并发保护。
- 本地自动化和 PostgreSQL 16 容器集成已经通过。

当前正在进行 B3。R1.1-R1.2 已完成代码和 PostgreSQL 16 容器验收：订单草稿、明细、待办和日志已落 PostgreSQL，识别、保存和阻断确认改为提交后更新工作区，旧 `revision` 返回 `409`。B3 仍未完成：正式订单确认与草稿状态目前还是两个连续事务，部分订单、库存、交付、对账启动工作区仍依赖 seed 或旧内存投影。

## 二、整改目标

1. production 的业务事实只来自 PostgreSQL 和对象存储。
2. 核心写链具备幂等、并发冲突、事务回滚和数据库提交版本回读。
3. API 重启、浏览器刷新和双会话操作后数据保持一致。
4. 六个办公室核心页面形成统一、高密度、可扫描的 ERP 工作台。
5. 大型组合文件按领域拆分，业务规则只有一个实现位置。
6. 真实打印、司机手机和业务试跑通过现场验收。
7. 发布门禁、现场证据和负责人签字全部完成后才宣布 V1 完成。

## 三、问题分级

### P0：必须先整改

| 问题 | 当前风险 | 主要位置 | 整改方向 |
| --- | --- | --- | --- |
| PostgreSQL 不是完整唯一事实源 | 重启后可能回到 seed，多个会话可能看到不同状态 | `server/apiServer.mjs`、订单草稿与核心读取仓储 | 新增草稿仓储和核心启动快照；数据库提交后再更新内存投影。 |
| 订单草稿仍以内存写入为主 | 草稿刷新丢失，旧页面可能覆盖新版本 | `recognizeOrderDraft`、`saveOrderDraft`、`confirmOrderDraftRoute` | 草稿、明细、待办和日志同事务保存；加入 `revision` 冲突。 |
| 真实基础设施未验收 | 本地容器通过不等于生产可恢复 | PostgreSQL、对象存储、部署脚本 | 执行真实迁移、备份恢复、对象存储读写和治理检查。 |
| 真实设备未验收 | 预览成功不等于真实出纸、扫码、定位成功 | 打印链、司机端 | Windows 11 打印主机和真实手机现场验证并留证。 |

### P1：P0 稳定后整改

| 问题 | 当前规模 | 整改方向 |
| --- | --- | --- |
| API 主入口过大 | `server/apiServer.mjs` 约 22,816 行 | 保留启动、中间件、依赖装配和路由装配；业务进入 service/domain。 |
| 办公室页面过大 | `src/pages/office/index.jsx` 约 13,046 行 | 按待办、订单、库存、交付、对账、生产、原材料拆页。 |
| 应用组合根过大 | `src/App.jsx` 约 10,467 行 | 收敛到应用壳、登录、路由和全局反馈。 |
| 样式集中且重复 | `src/styles.css` 约 8,916 行 | 提取 tokens、布局、表格、侧栏和领域样式；删除重复选择器。 |
| UI 模式不完全一致 | 标题栏、筛选、表格、侧栏、空态和错误态存在差异 | 建立共享组件和统一状态规则，不改变业务状态机。 |

### P2：V2 范围，V1 暂停扩展

- 售后责任分摊与绩效扣款。
- 工资、考勤和完整人事。
- 企业微信自动化和客户群自动发送。
- 高级 BI、路线优化和深度毛利分析。

这些模块保留需求和接口边界，不进入本轮 V1 主线。

## 四、执行批次

### R1：B3 PostgreSQL 唯一事实源

状态：`R1.1-R1.2 已通过；R1.3-R1.5 待执行`

| 轮次 | 修改内容 | 验收标准 |
| --- | --- | --- |
| R1.1（已通过） | 实现订单草稿 PostgreSQL 仓储；保存草稿、明细、待办和日志 | 同一事务提交；返回数据库 `revision`；失败无部分写入。 |
| R1.2（已通过） | 识别、保存和阻断确认改为仓储提交后更新工作区 | 不再先改内存；不存在草稿返回 404；旧版本返回 409。 |
| R1.3 | 正式订单确认同时更新草稿状态 | 草稿转正式订单和库存占用在同一事务边界。 |
| R1.4 | 增加核心 PostgreSQL 启动快照 | production 空库不得显示 seed 客户、订单、库存、交付或对账数据。 |
| R1.5 | 加入重启、双会话和并发验证 | API 重启后草稿可继续编辑；两个旧版本提交只有一个成功。 |

必须覆盖的集合：

- 客户、联系人、地址、标准颜色。
- 原始订单、订单明细、价格快照。
- 库存、占用和库存流水。
- 交付、异常、包裹和打印记录。
- 对账单、对账明细、待办、差额、发送和确认记录。
- 操作日志、订单改量 / 作废记录、生产任务、车间报工和打包任务。

退出条件：production 启动后核心数据完全来自 PostgreSQL；API 重启、浏览器刷新和双会话结果一致。

### R2：真实基础设施和可恢复部署

状态：`R1 后执行`

1. 在真实 PostgreSQL 执行迁移、checksum、并发事务和重复执行检查。
2. 在专用恢复验证库完成备份 / 恢复抽样，不允许重置生产库。
3. 在真实 OSS/S3/COS 验证附件和对账文件的写入、读回、签名访问、删除、版本控制、生命周期和加密。
4. 配置受控 Git 远端，在全新目录完成 clone、安装、构建和启动恢复。
5. 建立 API / Web 启停、日志、健康检查、告警、备份和回滚手册。

退出条件：真实服务报告通过且保持脱敏；代码和数据均可在另一台受控主机恢复。

### R3：真实打印和司机设备

状态：`R2 后执行`

1. 配置 Windows 11 打印主机和 `EPSON LQ-615KII`。
2. 确认系统打印机名、驱动、端口、队列、纸张尺寸、页边距和对位参数。
3. 对单据、快递 / 快运标签和原材料防水标签执行真实出纸、扫码、作废重打和状态回读。
4. 在司机真实手机验证登录、原生扫码、相机、定位、导航、水印、弱网和送达证据。

退出条件：打印门禁和司机真机门禁通过，并有样张、设备结果和负责人复核。

### R4：真实业务试跑

状态：`R3 后执行`

至少覆盖：

- 现货、缺货、定制印刷和外协订单。
- `白印黑`、`白袋黑提`、`黄袋红提`、单双面和备注。
- 库存占用、释放、改量、作废、补货、生产、报工和打包。
- 自提、送货、快递快运、数量不符和无法出库。
- 对账、发送、收款、差额、核销、附件和 Excel 导出。
- 原材料送货单、复核、一卷一标、扫码、领料、余料和供应商月结。

退出条件：办公室、库房、车间、司机和财务用脱敏真实样本完成主流程及异常流程。

### R5：代码精简

状态：`R1 可小步开始，R4 后集中收口`

1. 先提取纯函数、状态映射和 DTO，不同时改业务规则。
2. `apiServer.mjs` 按订单、库存、交付、对账、生产、原材料、打印、司机、系统拆 service。
3. `office/index.jsx` 按页面拆分，URL、权限和 API 调用保持不变。
4. `App.jsx` 只保留应用壳、会话、路由和全局反馈。
5. API client 提取请求、分页、错误和 stale revision 公共处理。
6. 删除代码前用 `rg` 证明无调用，并用专项测试和构建兜底。

建议结构目标，不作为单纯行数 KPI：

- 组合入口尽量控制在 1,500 行以内。
- 单个领域 service / repository 尽量控制在 1,200 行以内。
- 超过目标时必须能说明该文件只有一个清晰职责，而不是机械拆文件。

### R6：UI 重构

状态：`R4 业务稳定后集中执行`

#### 统一骨架

- 窄左侧导航 + 顶部页面标题 / 动作栏。
- 六个办公室核心页优先显示，后续模块保持灰色二级入口。
- 统一 `PageHeader`、`FilterBar`、`DataTable`、`StatusTag`、`DetailsPanel`、`EmptyState`、`ErrorState` 和 `LoadingState`。
- 卡片只用于单个重复项、弹窗和确需边框的工具，不使用大卡片堆叠页面。

#### 页面顺序

1. 公共待办：提高扫描、批量处理和异常优先级。
2. 订单录入：保留大文本识别区、行内编辑和复杂印刷侧栏。
3. 订单池：统一筛选、状态、详情和跨模块定位。
4. 库存查询：突出可用、占用、缺货、待处理及流水。
5. 出库交付：突出今日、异常、待打印、待拉走和下一步动作。
6. 对账收款：保持左侧客户、右侧账期订单和收款状态。

#### 视觉和交互规则

- 高密度 SaaS ERP 风格，不做营销页、大留白或装饰性渐变。
- 库存状态固定为：可用绿色、占用黄色、缺货红色、待处理灰色。
- 公共状态固定为：正常蓝 / 绿、待处理黄、异常红、完成弱绿、作废灰。
- 图标按钮使用现有图标库并提供 tooltip；二元设置使用开关或复选框。
- 桌面表格保持紧凑；手机端改为可操作的行摘要和详情，不强行压缩完整表格。

验收视口：`1280x720`、`1440x900`、`1920x1080`、`390x844`。

退出条件：无横向页面溢出、文字 / 按钮 / 侧栏重叠；加载、空、错误和无权限状态齐全；控制台错误为 0。

### R7：证据、签字和发布

状态：`最后执行`

1. 回填现场证据 `34/34`。
2. 完成负责人签字 `6/6`。
3. 重新生成 release candidate、go-live suite 和 handoff pack。
4. 发布门禁达到 `4/4` 后安排灰度上线窗口。
5. 上线前执行备份恢复、版本回滚和故障联系人演练。

## 五、自动化验收

每轮至少执行与修改范围对应的专项检查，并在批次结束执行：

```bash
npm run lint
npm run build
npm test
npm run batch-b:check
npm run db:postgres-live:check
git diff --check
```

UI 轮次还必须执行：

- 桌面和手机截图对比。
- 浏览器控制台错误检查。
- 页面与关键容器横向溢出检查。
- 主要操作、空态、错误态和无权限态检查。

真实环境、打印机和手机未实际执行时，结论必须写“未验证”，不能用本地自动化代替。

## 六、每轮交付格式

每轮完成后固定向负责人汇报：

1. 本轮修改了什么。
2. 解决了什么问题。
3. 还有什么问题没有修改。
4. 执行了哪些验证，结果如何。
5. 门禁、证据和签字数字是否变化。
6. 下一轮建议、风险和需要谁配合。

## 七、当前立即执行项

下一轮执行 R1.3-R1.4：

1. 把正式订单、明细、库存占用、库存流水、草稿状态和操作日志合并到同一确认事务。
2. 删除正式确认成功后的第二次草稿保存，消除“订单已提交但草稿状态保存失败”的窗口。
3. 增加 production 核心启动快照，空数据库不得显示 seed 客户、订单、库存、交付或对账数据。
4. 增加确认事务失败回滚、API 重启和双会话旧版本测试。
5. 暂不同时重构 UI，避免数据行为和视觉行为一起变化。

R1.3-R1.4 通过后，再执行完整 API 重启 / 双会话验收 R1.5。

## 八、上线红线

以下任一项存在时，不得宣布 V1 完成：

- production 仍可把 seed、内存、JSON 或本地文件当正式事实源。
- 正式环境仍可使用 seed 账号、身份 Header 或前端本地写入回退。
- 重复请求可能重复扣库存、收款、核销、打印或派送。
- 打印只有预览，没有真实出纸、扫码和状态回读。
- 司机端只有浏览器模拟，没有真实手机权限和现场证据。
- PostgreSQL、对象存储、备份恢复、远端恢复或回滚演练未完成。
- 现场证据、负责人签字或 V1/V2 边界未确认。
- 真实密钥、连接串、bucket、token、命令或本机路径进入 Git 和普通报告。
