# ERP 系统代码与 UI 整改方案

制定日期：2026-07-11
版本：V7.30
适用范围：V1 上线收口、代码精简、UI 统一和现场验收

执行口径：本方案按“代码质量整改”和“真实上线验收”双轨推进。代码、自动化和本地预览通过，不等于真实生产环境、打印机、司机手机和现场业务已经验收。

## 零、执行摘要

本轮整改不推翻现有业务代码，也不做一次性全站换肤。现有六个办公室主页面、角色工具、权限、事务和大部分领域 API 已具备，整改重点是把仍留在组合根中的职责迁出、统一操作型 UI，并完成真实环境与现场门禁。

按以下顺序执行：

1. **R1 打印写入收口**：迁出 `App.jsx` 中最后一组打印写动作；明确区分“预览 / 已提交打印作业 / spool 已接收 / 实体已出纸”，预览不得推进真实交付状态。
2. **R2 App 壳层收口**：把剩余页面装配、弹窗和领域状态迁到 feature / hook；`App.jsx` 只保留会话、导航、路由、全局反馈和依赖装配。
3. **R3 共享 UI 骨架**：先建立页面头、筛选条、紧凑表格、状态标签、详情面板、空 / 错误 / 无权限状态，不直接改业务状态机。
4. **R4-R6 逐页 UI 重构**：先公共待办与订单，再库存与出库，最后对账与角色工具；每页独立截图、浏览器交互和回归。
5. **R7 API / CSS 拆分**：按领域迁移 service，按层拆 CSS；不在结构迁移中顺手修改业务规则。
6. **R8 真实上线验收**：真实 PostgreSQL、恢复验证库、对象存储、打印 / CUPS、司机真机、真实订单试跑、证据和签字全部闭环。

R1、R2 的 D21 交互控制器、D22 共享 UI 首轮、D23 三个操作页、D24 对账 / 角色工具迁移、D25-1 V1 状态模块首轮拆分、D25-2 / D25-6 打印域 service、D26 公共待办处理持久化、D27 库存修正 / 生产成品图来源事务、D28 生产报工 / 跨日报数 / 打包事务、D29 排产事务硬化、D30-D31 生产 command service、D32 对账通信写链、D33 认证身份边界、D34-D35 订单明细事务 / service、D36 订单草稿 / 确认 service、D37-D38 出库 / 派单 / 司机交付 command service、D39 司机送达凭证附件可信校验、D40 共享业务附件校验 / 定制成品图、D41 财务 / 客户确认附件收口和 D42 库存修正附件持久化关联已完成；当前进入 D43 隔离数据核心浏览器 E2E。R8 需要现场真实配置和设备配合，可与其余代码整改并行，但不能由本地模拟代替。

D24 已把对账、生产 / 打包、原材料、车间和司机页接入共享运营 UI。对账保留五项财务口径；生产保留“机器计数不是合格产量”边界；原材料保留 OCR 仅预填、一卷一标、贴标扫码后可用；司机页按当前状态隔离任务。浏览器验收还发现并修复了司机切换到无任务状态时原生联调摘要读取 `null.items` 导致白屏的问题，并加入回归测试。

D26 已将八类公共待办处理动作迁入 `todoCommandService.mjs` 和 `todoActionRepository.mjs`。production 在同一 PostgreSQL 幂等事务内更新 `todos`、追加完整 `todo_events` 并写操作日志，增加待办资源锁和 `updated_at` 陈旧快照门禁；认证操作人覆盖请求体身份。核心启动读模型合并最新事件，通知、打印核对和提醒细节可跨重启恢复。repository 已纳入 production 强制 PostgreSQL profile 和系统 readiness。直接 service / repository、实际 HTTP、全量构建与 PostgreSQL 16 重放 / 重启 live 均已通过。

D27-1 已将库存修正从 API 组合根内连续修改内存，迁为 `inventoryCorrectionCommandService.mjs` 和 `inventoryCorrectionTransactionRepository.mjs`。创建阶段原子写修正草稿、待办、完整待办事件和操作日志，不提前修改库存；确认阶段原子更新库存与草稿、写库存流水、处理待办并追加事件和日志。production 使用共享幂等、库存 / 修正单 / 待办资源锁和 revision 门禁；认证操作人覆盖请求体身份。迁移 `0013` 补齐待办关联、备注和附件，重启后详情可恢复。下一轮 D27-2 迁移生产成品图审核任务和待办来源。

D27-2 已将成品图上传 / 审核迁入 `productionFinishedGoodsPhotoCommandService.mjs` 和 `productionFinishedGoodsPhotoTransactionRepository.mjs`。上传原子写任务图片快照和日志；审核原子写任务、客户通知 / 重拍待办、自动解决的旧重拍待办、完整事件和日志。迁移 `0014` 增加任务 revision 和 JSONB 图片快照，两个读模型均支持重启恢复；production 使用共享幂等、任务 / 待办资源锁和认证操作人。API 主文件的旧双份逻辑已删除。

D28 已将生产完工报工、跨日进度和打包完成统一到共享 PostgreSQL 幂等执行器。迁移 `0015` 增加打包任务 revision；生产任务、订单行、库存、打包任务和交付记录分别行锁并校验版本 / 数量快照，终态重复写入被拒绝。所有修改 CTE 依赖物化 `write_guard`，避免同语句执行顺序导致旧版本误判；对象级冲突统一映射 409。写后库存和产能使用权威绝对值更新内存投影，跨日报数使用首次持久化 evidence 返回稳定结果。三个路由只接受认证身份作为审计操作人。下一轮 D29 处理仍使用普通事务或请求体身份的排产发布、同机台调序和跨机台移动。

D29 已将排产发布、同机台调序和跨机台移动统一到认证身份、共享 PostgreSQL 幂等执行器及机台 / 任务资源锁。迁移 `0016` 为排产记录增加 revision；调序和移机会锁定并校验涉及机台的完整排产记录集合，任何记录新增、缺失或版本变化均返回 409。移机同步递增生产任务 revision，发布排产使用任务 / 订单行写保护；队列 GET 每次从仓储刷新排产记录，避免多实例继续使用启动快照。幂等响应保留首次事务上下文和日志，且不创建库存、占用、打包或合格产量。下一轮 D30 只迁移排产业务编排到独立 command service，不改变状态机、事务 SQL 或权限。

D31 已新增 `productionReportingCommandService.mjs` 和 `packingCommandService.mjs`，把生产完工报工、跨日报数和打包完成的校验、数量计算、记录 / 审计构造和 repository 调用从 API 组合入口迁出。三个 HTTP handler 只调用 service 并映射结果；`apiServer.mjs` 减少 544 行。直接测试锁定机器计数不进入合格产量 / 库存、报工只按合格数量入库、打包不重复扣库存、幂等上下文和认证身份。测试同时发现并修复包裹 `createdBy` 可被请求体伪造的问题，现统一使用认证操作人。下一轮 D32 审计并收口对账预览、发送、回执和客户确认的身份、幂等及 service 边界。

D33 已统一订单、出库、打印以及相关原料 / 主数据写路由的认证身份边界。订单草稿识别 / 保存 / 确认、订单明细作废 / 改量、出库异常 / 派单 / 打印 / 备货 / 完成 / 拉走 / 取消 / 证据复核、打印设备维护、人工打印作业状态 / 派发 / 重试和打印记录作废，全部由路由传入认证操作人；API 与 command service 不再把请求体 `operatorId` 用于记录、审计或幂等 payload。打印驱动回调的自由文本身份只保留为 reported metadata。OpenAPI 已把兼容身份字段改为非必填并标记废弃。直接 route / service、防伪 HTTP、PostgreSQL 操作日志、全量测试、构建和 production profile live 通过。审核同时确认 `orderLineVoidTransactionRepository` 与 `orderLineQuantityAdjustmentTransactionRepository` 仍是普通事务，传入的幂等参数尚未消费，也没有对象锁和 revision 门禁；下一轮 D34 专门补齐该并发边界。

D34 已将订单明细作废 / 改量接入共享 PostgreSQL 幂等执行器。迁移 `0018` 为库存预留和对账明细增加 revision；事务按订单行、交付、预留、库存和对账单加稳定资源锁，锁行后校验 revision、预留数量 / 状态、库存占用及对账数量 / 金额快照，冲突统一返回 409 且事务回滚。API 在终态校验前读取已完成幂等结果，支持同键稳定重放并拒绝同键换内容。订单确认返回并投影写后库存绝对数量与 revision，修复确认后工作区库存版本落后问题。下一轮 D35 把作废 / 改量的业务校验、记录构造和 repository 编排迁入独立 command service，不改变 D34 事务合同。

## 一、整改结论

当前系统不是未开发原型，也不是已经完成的生产系统。准确状态如下：

| 维度 | 当前判断 | 说明 |
| --- | --- | --- |
| P0 原型 / 代码能力 | `97-98%` | 六个办公室主页面、角色工具、核心 API、权限和主要事务链已经具备。 |
| V1 上线就绪 | `80-83%` | 真实基础设施、硬件、业务试跑、证据和签字未闭环。 |
| 发布门禁 | `0/4` | 当前不能宣布 V1 完成或正式上线。 |

## 二、整改原则

1. **先保业务，再拆结构**：每轮只移动一个领域的职责，不同时修改业务状态机。
2. **服务端事实优先**：production 不得用 seed、内存、JSON、本地文件或浏览器投影代替正式事实源。
3. **先建立共享骨架，再逐页改 UI**：避免六个页面分别产生新的重复样式。
4. **真实验收单独计数**：本地测试通过不增加现场证据、签字和发布门禁数字。
5. **小批次可回退**：每轮必须可独立测试、独立提交、独立回退。
6. **不扩展 V2**：售后绩效、工资考勤、企业微信自动化、高级 BI 和路线优化不进入本轮。

#### B2 API 业务实现拆分

现有 routes 只完成了多数 HTTP 分发，下一步按领域迁移业务实现：

1. 订单与库存。
2. 出库交付与打印。
3. 对账收款与附件。
4. 生产打包与原材料。
5. 司机与主数据。
6. V1 上线状态与执行器。

每个领域形成 `route -> service -> repository`：

- route：解析请求、认证、权限、HTTP 状态和响应。
- service：业务规则、事务编排、幂等和冲突映射。
- repository：参数化 SQL、锁、提交版本和持久化投影。

退出条件：`apiServer.mjs` 不再包含领域业务实现；专项测试和 PostgreSQL live 检查通过。

执行时不以“行数下降”作为唯一成功标准。每迁移一个领域必须同时满足：

- route 不读取浏览器伪造的身份、文件路径、命令或生产环境值。
- service 可以注入 repository / clock / idempotency，并能脱离 HTTP 直接测试。
- repository 继续使用共享异步 PostgreSQL pool、参数绑定和事务锁。
- 原 HTTP 合同、错误码、权限、操作日志和响应投影保持兼容。

## 六、验收与质量门禁

每个代码轮次至少执行对应专项，并在轮次结束执行：

```bash
npm run lint
npm run build
npm test
git diff --check
```

涉及数据库事务时追加：

```bash
npm run batch-b:check
npm run db:postgres-live:check
```

涉及 UI 时追加浏览器桌面 / 手机验证、控制台检查和横向溢出检查。

真实环境、打印机或手机未实际执行时，交付结论必须写“未验证”，不得用模拟结果代替。

### 完成定义

单个整改轮次只有同时满足以下条件才算完成：

1. 功能行为与权限合同未被无意改变；有意改变必须同步需求和决策记录。
2. production 网络失败、权限拒绝或冲突时不得写入浏览器成功投影。
3. 专项测试、`npm test`、构建和差异检查通过。
4. 涉及 UI 的页面完成桌面和 `390x844` 浏览器验证，无溢出、重叠和应用控制台错误。
5. 文档同步记录本轮已改、未改、验证和下一步。
6. 真实门禁数字只依据真实证据变化，不因代码或模拟通过而增加。

## 九、上线红线

以下任一项存在时，不得宣布 V1 完成：

- production 仍可把 seed、内存、JSON 或本地文件当正式事实源。
- 正式环境仍可使用 seed 账号、身份 Header 或浏览器本地业务写入回退。
- 重复请求可能重复扣库存、收款、核销、打印或派送。
- 打印只有预览，没有真实出纸、扫码和状态回读。
- 司机端只有浏览器模拟，没有真实手机权限和现场证据。
- PostgreSQL、对象存储、备份恢复、远端恢复或回滚演练未完成。
- 现场证据、负责人签字或 V1 / V2 边界未确认。
- 真实密钥、连接串、bucket、token、命令或本机路径进入 Git 和普通报告。
