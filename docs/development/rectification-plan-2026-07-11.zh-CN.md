# ERP 系统代码与 UI 整改方案

制定日期：2026-07-11
版本：V7.6
适用范围：V1 上线收口、代码精简、UI 统一和现场验收

执行口径：本方案按“代码质量整改”和“真实上线验收”双轨推进。代码、自动化和本地预览通过，不等于真实生产环境、打印机、司机手机和现场业务已经验收。

## 零、执行摘要

本轮整改不推翻现有业务代码，也不做一次性全站换肤。现有六个办公室主页面、角色工具、权限、事务和大部分领域 API 已具备，整改重点是把仍留在组合根中的职责迁出、统一操作型 UI，并完成真实环境与现场门禁。

按以下顺序执行：

1. **R1 打印写入收口**：迁出 `App.jsx` 中最后一组打印写动作；明确区分“预览 / 已提交打印作业 / spool 已接收 / 实体已出纸”，预览不得推进真实交付状态。
2. **R2 App 壳层收口**：把剩余页面装配、弹窗和领域状态迁到 feature / hook；`App.jsx` 只保留会话、导航、路由、全局反馈和依赖装配。
3. **R3 共享 UI 骨架**：先建立页面头、筛选条、紧凑表格、状态标签、详情面板、空 / 错误 / 无权限状态，不直接改业务状态机。
4. **R4-R6 逐页 UI 重构**：先公共待办与订单，再库存与出库，最后对账与角色工具；每页独立截图、浏览器交互和回归。
5. **R7 API / CSS 拆分**：按领域迁移 service，按层拆 CSS；不在结构迁移中顺手修改业务规则。
6. **R8 真实上线验收**：真实 PostgreSQL、恢复验证库、对象存储、打印 / CUPS、司机真机、真实订单试跑、证据和签字全部闭环。

R1、R2 的 D21 交互控制器、D22 共享 UI 首轮、D23 三个操作页、D24 对账 / 角色工具迁移和 D25-1 V1 状态模块首轮拆分已完成，当前进入 D25-2 打印 / 交付 API service 首轮迁移；R8 需要现场真实配置和设备配合，可与其余代码整改并行，但不能由本地模拟代替。

D24 已把对账、生产 / 打包、原材料、车间和司机页接入共享运营 UI。对账保留五项财务口径；生产保留“机器计数不是合格产量”边界；原材料保留 OCR 仅预填、一卷一标、贴标扫码后可用；司机页按当前状态隔离任务。浏览器验收还发现并修复了司机切换到无任务状态时原生联调摘要读取 `null.items` 导致白屏的问题，并加入回归测试。

D25-1 已把 V1 状态页的静态完成度基线、阶段归一、快照新鲜度和生产 env 变量检查迁入纯展示模型，把顶部快照 / 发布门禁 / 模块列表迁入独立组件；客户端把 22 个 HTTP action 收敛为显式配置的 action factory，原文件只保留 normalizer 和兼容导出。action factory 直接覆盖幂等请求头、权限拒绝、ready=false 阻断和离线 fail-closed；管理 / 技术运维可见、办公室不可见的权限边界保持。

## 二、整改原则

1. **先保业务，再拆结构**：每轮只移动一个领域的职责，不同时修改业务状态机。
2. **服务端事实优先**：production 不得用 seed、内存、JSON、本地文件或浏览器投影代替正式事实源。
3. **先建立共享骨架，再逐页改 UI**：避免六个页面分别产生新的重复样式。
4. **真实验收单独计数**：本地测试通过不增加现场证据、签字和发布门禁数字。
5. **小批次可回退**：每轮必须可独立测试、独立提交、独立回退。
6. **不扩展 V2**：售后绩效、工资考勤、企业微信自动化、高级 BI 和路线优化不进入本轮。

## 四、执行路线

整改分成 A、B、C 三条轨道。A 是生产上线主线；B、C 可以并行，但不能替代 A 的验收。

### A 轨：生产上线收口

#### A1 真实基础设施

1. 填写安全 production env，保持未跟踪、`0600` 和报告脱敏。
2. 连接真实 PostgreSQL，执行迁移计划、checksum、权限和重复执行检查。
3. 在专用可重置恢复验证库执行备份 / 恢复抽样，禁止重置生产库。
4. 连接真实 OSS / S3 / COS，执行附件与对账导出的读写和治理检查。
5. 配置受控 Git 远端，完成全新目录 clone、安装、构建、迁移计划和启动恢复。

退出条件：生产持久化证据、runtime smoke 和第一阶段 closeout 全部通过。

#### A2 真实设备

1. 配置 Windows 11 打印主机、驱动、端口、队列、纸张和页边距。
2. 验证单据、快递 / 快运标签和原材料防水标签的真实出纸、对位、扫码、作废重打和状态回读。
3. 在司机真实手机验证登录、扫码、相机、定位、导航、水印、弱网和送达证据。

退出条件：打印 closeout 和司机真机 closeout 均为 ready，并保留脱敏证据。

#### A3 真实业务试跑

必须覆盖：

- 现货、缺货、定制印刷和外协订单。
- `白印黑`、`白袋黑提`、`黄袋红提`、单双面和其他备注。
- 库存占用、释放、改量、作废、补货、生产、报工和打包。
- 自提、送货、快递快运、数量不符和无法出库。
- 对账、发送、收款、差额、核销、附件和 Excel 导出。
- 原材料送货单、复核、一卷一标、扫码、领料、余料和供应商月结。

退出条件：办公室、仓库、车间、司机和财务分别完成主流程及异常流程验收。

#### A4 发布收口

1. 回填现场证据 `34/34`。
2. 完成负责人签字 `6/6`。
3. 重新生成 release candidate、go-live suite 和 handoff pack。
4. 发布门禁达到 `4/4` 后安排灰度上线。

#### B2 API 业务实现拆分

现有 routes 只完成了多数 HTTP 分发，下一步按领域迁移业务实现：

1. 订单与库存。
2. 出库交付与打印。
3. 对账收款与附件。
4. 生产打包与原材料。
5. 司机与主数据。
6. V1 上线状态与执行器。

每个领域形成 `route -> service -> repository`：

- route：解析请求、认证、权限、HTTP 状态和响应。
- service：业务规则、事务编排、幂等和冲突映射。
- repository：参数化 SQL、锁、提交版本和持久化投影。

退出条件：`apiServer.mjs` 不再包含领域业务实现；专项测试和 PostgreSQL live 检查通过。

执行时不以“行数下降”作为唯一成功标准。每迁移一个领域必须同时满足：

- route 不读取浏览器伪造的身份、文件路径、命令或生产环境值。
- service 可以注入 repository / clock / idempotency，并能脱离 HTTP 直接测试。
- repository 继续使用共享异步 PostgreSQL pool、参数绑定和事务锁。
- 原 HTTP 合同、错误码、权限、操作日志和响应投影保持兼容。
