# ERP 代码、上线与 UI 整改执行方案

制定日期：2026-07-12
版本：V8.0
适用范围：V1 小范围真实上线、代码精简、UI 重构、现场验收

## 一、整改结论

当前系统不能判定为“全部完成”，但也不是只有页面的空原型。

| 维度 | 当前基线 | 结论 |
| --- | --- | --- |
| 需求确认 | `85-90%` | V1 主流程较清楚，少量现场规则仍需试跑确认。 |
| P0 原型 / 代码 | `97-98%` | 六个办公室主页面、角色工具、核心 API、权限和主要事务链已具备。 |
| V1 上线就绪 | `80-83%` | 真实基础设施、设备、业务试跑、证据和签字未闭环。 |
| 发布门禁 | `0/4` | 当前禁止宣布正式完成或上线。 |
| 现场证据 | `0/34` | 自动化报告不能替代真实出纸、扫码、定位和业务样本。 |
| 负责人签字 | `0/6` | 办公室、仓库、车间、司机、财务、管理尚未签收。 |

代码结构仍有明显集中点：

| 文件 | 当前规模 | 整改目标 |
| --- | ---: | --- |
| `src/App.jsx` | `7,231` 行 | 只保留会话、导航、路由、全局反馈和依赖装配；领域状态和动作迁入 feature/controller。 |
| `server/apiServer.mjs` | `18,365` 行 | 只保留启动、依赖注入和路由装配；业务规则迁入 service，SQL 和事务留在 repository。 |
| `src/styles.css` | `9,002` 行 | 降为兼容入口或删除；样式按 token、壳层、控件、表格、面板、状态、移动端和 feature 分层。 |

## 二、整改原则

1. 先守住生产安全和数据一致性，再做视觉优化。
2. 上线主线、代码结构和 UI 三轨并行，但 UI 完成不能替代真实上线验收。
3. 每轮只处理一个清晰边界，不在结构迁移中顺手改业务状态机。
4. 不以删行数作为唯一目标；必须同时降低重复、职责耦合和测试成本。
5. 生产环境必须 fail-closed：认证、数据库、对象存储或后端写入失败时，不得显示本地模拟成功。
6. 所有敏感值只进入未跟踪且权限受控的安全 env；报告、命令参数和交接包不得泄露 token、密码、连接串或真实路径。
7. V1 不新增工资、考勤、企微自动化、BI、路线优化和完整售后中心。

## 三、问题分级

### P0：上线阻断问题

| 问题 | 当前情况 | 整改动作 | 完成标准 |
| --- | --- | --- | --- |
| 生产验收身份 | 正式员工账号和 production 门禁已具备；部分 readiness 工具仍在收口正式登录态。 | 生产只接受 runtime session 或正式账号登录；移除 `x-erp-user-id` 依赖；token 不进入子进程参数和报告。 | production 缺正式身份直接阻断；认证专项、预检和 runtime smoke 全部通过。 |
| 真实生产环境 | 本地 PostgreSQL / 对象存储 live 已验证，真实生产值和长驻服务未验收。 | 填写安全 env、执行迁移、备份恢复、对象存储读写和治理检查，启动长驻 API。 | production profile 全为 PostgreSQL / object storage；重启后数据可恢复；第一阶段 closeout ready。 |

| 司机真机 | 原生桥合同和 readiness 门禁已有，真实 Android/iOS 验收缺失。 | 验证登录、扫码、相机、定位、导航、水印、弱网重传和送达证据。 | 司机真机 closeout ready，任务归属和附件可信校验通过。 |
| 真实业务试跑 | 自动化核心闭环已覆盖，真实业务样本未签收。 | 按岗位跑现货、缺货、定制、外协、出库、对账、原料和异常流程。 | 34/34 证据、6/6 签字、4/4 发布门禁全部完成。 |

### P1：代码质量和维护成本

| 问题 | 整改方式 | 验收重点 |
| --- | --- | --- |
| `App.jsx` 过大 | 按领域迁出 controller、状态和 modal 编排；页面只接收明确 props。 | 登录、权限、导航和现有动作合同不变；专项测试与浏览器 E2E 通过。 |
| `apiServer.mjs` 过大 | 按 `route -> service -> repository` 迁移剩余业务实现。 | route 不直接堆业务规则或 SQL；service 可注入测试；repository 保留事务、锁和参数化 SQL。 |
| CSS 主入口过大 | 先做选择器调用盘点，再分层迁移和删除重复规则。 | 无视觉回归、无未使用选择器误删、桌面和手机无横向溢出。 |
| 页面模式不统一 | 复用已有运营 UI 骨架，补 `FilterBar`、紧凑表格和动作栏能力。 | 页面密度一致，状态、空态、错误态、无权限态一致。 |
| 测试入口偏大 | 为纯函数、action factory、service、repository 和 E2E 分层。 | 小改动可跑专项，发布前仍跑全量、PostgreSQL live 和核心 E2E。 |

### P2：V2 暂缓项

- 售后责任分摊、绩效扣款和完整售后中心。
- 工资、考勤和完整人事。
- 企业微信会话存档、客户群自动发送和自动回调。
- 高级 BI、自动排产、路线优化和深度毛利分析。

## 四、执行轨道

### A 轨：生产上线收口

#### A1 正式身份与运行态认证

- 生产 readiness、runtime smoke、release candidate、field acceptance 和 suite 统一使用正式 session。
- 办公室和司机使用各自账号，禁止共用高权限账号。
- CLI 仅保留兼容参数，推荐通过安全 env 注入；不得把 token 传给子进程命令行。
- 报告只输出认证来源、账号匹配结果和布尔安全护栏。

退出条件：正式认证专项、env preflight、runtime smoke、release candidate 工具链全部通过。

#### A2 真实基础设施

1. 导入 8 类岗位真实员工，完成复核、首次改密、账号有效期和车间默认机器绑定。
2. 填写并审计 production 安全 env，保持未跟踪和 `0600`。
3. 在真实 PostgreSQL 执行迁移、checksum、权限和备份恢复演练。
4. 在真实对象存储执行附件 / 对账导出写入、读回、签名 URL、删除和治理检查。
5. 启动长驻 API，验证进程守护、反向代理、TLS、健康检查、日志和重启恢复。

退出条件：生产持久化证据、runtime smoke 和第一阶段 closeout 均为 ready。

#### A3 真实设备

1. 打印机：队列、驱动、端口、纸张、边距、条码、状态回读和作废重打。
2. 原材料标签：防水 / 耐潮 / 耐脏标签纸，一卷一标，贴标后手机扫码。
3. 司机手机：登录、相机、扫码、定位、导航、水印、弱网和重传。

退出条件：打印 closeout 和司机真机 closeout 均为 ready，证据已脱敏归档。

#### A4 业务试跑与放行

- 订单：现货、缺货、定制印刷、外协、改量、作废和补货。
- 定制：`白印黑`、`白袋黑提`、`黄袋红提`、单双面和其他备注。
- 生产：排产、报工、成品图、打包；机器计数不得进入合格产量。
- 交付：自提、送货、快递快运、数量不符、无法出库和取消。
- 财务：对账、发送、实收、差额、核销、附件和 Excel 导出。
- 原材料：送货单、OCR 预填、复核、一卷一标、领料、余料、成本和供应商月结。

退出条件：现场证据 `34/34`、负责人签字 `6/6`、发布门禁 `4/4`、V1/V2 边界已确认。

### B 轨：代码结构与精简

#### B1 前端组合根

目标结构：

```text
src/app/
  AppShell.jsx
  navigation.js
  useOfficeWorkspace.js
  controllers/
src/features/<domain>/
  *Page.jsx
  *Controller.js
  *Actions.js
src/shared/
  api/
  ui/
  labels.js
```

迁移顺序：附件 / 预览 -> V1 执行器 -> 页面装配 -> 领域弹窗 -> 领域状态。每迁一组都保留现有 API、幂等键、权限和错误提示合同。

#### B2 后端组合根

目标结构：

```text
server/routes/<domain>.mjs
server/services/<domain>CommandService.mjs
server/repositories/<domain>Repository.mjs
```

- route：认证、权限、参数解析、HTTP 状态和响应映射。
- service：业务资格、状态机、幂等上下文、事务编排和冲突映射。
- repository：参数化 SQL、行锁、revision、提交和持久化投影。

优先迁移剩余的 V1 上线状态 / 执行器、主数据、原材料和跨领域装配代码，不重复搬迁已独立的订单、生产、交付、打印和财务 command service。

#### B3 CSS 和共享组件

```text
src/styles/
  tokens.css
  shell.css
  controls.css
  table.css
  panel.css
  states.css
  mobile.css
  features/*.css
```

删除旧规则前必须先用 `rg` 确认调用点；共享组件只承载结构、可访问性和视觉规则，不承载业务权限或状态机。

### C 轨：UI 重构

#### C1 统一基线

- 窄左侧导航 + 顶部页面标题 / 动作栏。
- 高密度 SaaS ERP 操作台，不做大卡片、大留白或营销式首页。
- P0 主导航优先展示六页：公共待办、订单录入、订单池、库存查询、出库交付、对账收款。
- 生产、打包、原材料、司机、基础资料和上线状态按角色显示在二级入口。
- 统一状态颜色：正常蓝 / 绿、待处理黄、异常红、完成柔和绿、作废灰。

#### C2 页面整改顺序

1. App 壳层、导航、通知、权限空态。
2. 订单录入、订单池。
3. 库存查询、出库交付。
4. 对账收款、公共待办。
5. 生产 / 打包、原材料、司机、基础资料、上线状态。

每页必须覆盖 loading、empty、error、permission denied、正常数据、长文本和窄屏状态。

#### C3 业务显示规则

- 定制订单可见款式显示 `定制印刷`，库存匹配仍保留基础袋款。
- 出库货品摘要使用“品名 + 尺寸 + 紧凑颜色 + 单双面 + 数量 + 备注”。
- 颜色简写支持 `白印黑`、`白袋黑提`、`黄袋红提`；两者同时存在时显示 `白印黑 / 白袋黑提`。
- 内部枚举如 `pickup`、`delivery`、`express_ltl` 不得出现在可见表格。
- 机器计数只能显示为机器动作 / 周期计数，不能显示为合格产量、库存或计费数量。

## 六、统一验收标准

每轮代码变更至少执行：

```text
node --check / ESLint
受影响领域专项测试
npm test
npm run build
git diff --check
```

按影响范围追加：

- API 合同：OpenAPI 校验和实际 HTTP 回归。
- 数据事务：PostgreSQL 16 live、幂等重放、并发冲突和重启恢复。
- 核心闭环：Playwright 隔离数据 E2E。
- UI：`1280x720` 与 `390x844` 截图、控制台错误、横向溢出、可点击动作和空 / 错误 / 无权限状态。
- 生产工具：输出脱敏扫描，不在命令行、报告或交接包暴露敏感值。

## 七、每轮汇报格式

以后每次代码更新完成后，固定按以下格式汇报：

1. **本轮改了什么**：文件和行为变化。
2. **解决了什么问题**：原问题、修复结果和影响范围。
3. **还有什么没改**：明确列出未完成项和阻塞原因。
4. **做了什么验证**：测试命令、浏览器尺寸、实库 / 真机状态。
5. **当前完成度**：只在有真实依据时调整百分比。
6. **下一步建议**：给出下一轮唯一主任务，避免同时铺开过多范围。
