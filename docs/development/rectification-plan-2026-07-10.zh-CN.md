# ERP 系统整改实施方案

制定日期：2026-07-10

## 一、整改结论

当前系统可以用于高完成度 ERP 原型演示和业务流程确认，但不能作为已完成生产上线的系统。

- P0 代码完成度约 `97-98%`。
- V1 上线就绪度约 `80-83%`。
- 发布门禁 `0/4`、现场证据 `0/34`、负责人签字 `0/6`。
- Git 的 `367` 文件基线已提交为 `72f25c4`，当前工作区干净；仓库未配置远端，尚无本机外备份或远端恢复验证。
- `App.jsx` 约 `10,385` 行，办公室页面约 `13,046` 行，API 主入口约 `22,703` 行，仍需持续模块化。

整改目标不是继续增加原型页面，而是先形成可恢复代码基线，完成真实生产环境、设备和现场验收，再决定 V2 模块投入。

## 二、已完成整改

以下问题已经在当前代码中处理，不应重复开发，只需在正式环境重新验收：

1. 严格认证模式关闭 seed 用户、伪造身份 Header、伪造权限 Header 和默认办公室身份。
2. 严格模式要求正式 session，CORS 使用生产白名单，缺少认证密钥时拒绝生产启动。
3. Web token 已从长期 `localStorage` 改为会话级存储。
4. 生产模式写操作以后端事务结果为唯一事实来源，API 失败时不会本地伪造成功记录。
5. PostgreSQL 仓储已统一为异步连接池、参数化 SQL 和事务，不再使用同步 `psql` 子进程。
6. HTTP JSON 请求体已增加声明长度和累计字节硬限制。
7. 打印和司机 closeout 产物路径已统一脱敏，专项回归通过。
8. API 路由已按认证、订单、库存、交付、对账、打印、司机、生产、原材料和系统等领域拆分第一轮。
9. 前端 API client 已共享请求核心；生产/打包、打印、主数据和原材料列表状态已开始从大型页面中拆出。
10. `npm test`、lint、生产构建、OpenAPI 校验和浏览器重载检查均已通过。

## 四、四阶段实施计划

预计总周期为 `11-17` 个工作日。阶段 A 必须先完成；阶段 B 的数据库、对象存储、打印和司机真机可在环境就绪后并行；阶段 C 必须使用阶段 B 已验证的真实环境；阶段 D 只能在前三阶段退出条件全部满足后开始。

### 阶段 A：代码基线和生产配置（1-2 个工作日）

1. 已按运行/数据层、前端、文档和 CI 四组复核基线内容。
2. 已确认 `.erp-local-storage/`、截图、构建产物、真实 `.env*`、token、连接串和对象存储地址未进入 Git。
3. 已创建本地基线 commit `72f25c4`；配置受控远端、推送和全新 clone 恢复验证待完成。
4. 使用生产环境模板填写真实配置，只在受控主机保存。
5. 本地严格认证、CORS、请求体限制和敏感信息扫描已通过；生产 env 审计留档已补齐路径脱敏。录入真实配置后仍须在受控主机复跑。

验收命令：

```sh
git diff --cached --check
npm ci
npm test
npm run api:validate-openapi
```

阶段退出条件：代码可从远端恢复，生产配置来源明确，真实密钥未进入仓库。

### 阶段 B：真实基础设施与设备（3-5 个工作日）

1. 在真实 PostgreSQL 执行迁移、事务、并发、备份和恢复验证。
2. 在真实 OSS/S3/COS 验证附件、对账导出、签名访问、保留策略和审计日志。
3. 配置 Windows 11 打印主机、`EPSON LQ-615KII`、标签打印机和 CUPS/打印桥接队列。
4. 完成针式纸对位、标签尺寸、条码可扫、作废重打和状态回读。
5. 在司机手机完成原生扫码、原生导航、相机、定位、水印与签收证据检查。

阶段退出条件：PostgreSQL、对象存储、打印和司机真机四类真实门禁均有可追溯报告，不使用模拟报告代替。

### 阶段 C：真实业务试跑与 UI 整改（5-7 个工作日）

业务试跑至少覆盖：

1. 库存现货订单、缺货订单和定制印刷订单。
2. `白印黑`、`白袋黑提`、`黄袋红提` 等定制规格识别。
3. 生产排产、报工、成品图、打包和包裹标签。
4. 自提、送货、快递快运和数量差异。
5. 对账、收款、差额、核销和附件留档。
6. 原材料拍照、OCR 预填、复核、一卷一标、贴标扫码、机边领料、余料复核和供应商对账。

UI 整改同步执行，但不得改变业务状态机：

- `App.jsx` 拆为页面控制器 hooks、共享弹窗和应用壳。
- `pages/office/index.jsx` 按待办、订单、库存、出库、对账、生产、原材料和基础资料拆文件。
- 统一顶部操作栏、筛选区、表格密度、状态色、详情侧栏、加载态、错误态和空态。
- 保持 ERP 高密度工作台，不改成大卡片或营销型页面。
- 桌面优先，同时验证 1280px、1440px、1920px 和窄屏不重叠、不横向溢出。

阶段退出条件：核心流程真实试跑通过，UI 重构前后业务结果一致，控制台无错误，关键页面有截图证据。

### 阶段 D：证据、签字和发布（2-3 个工作日）

1. 逐项回填 34 项现场证据，不接受“代码已有”代替“现场已验证”。
2. 办公室、库房、司机、财务、车间和管理层完成 6 项签字。
3. 重新生成 V1 go-live suite、handoff pack 和发布候选报告。
4. 确认发布门禁达到 `4/4`，证据达到 `34/34`，签字达到 `6/6`。
5. 做一次回滚演练，并明确上线窗口、联系人和故障处理方式。

阶段退出条件：发布候选报告明确为 ready，且所有结论来自真实环境和现场证据。

## 五、模块处理原则

### 本轮必须完成

- 六个办公室核心页的真实数据闭环。
- 生产、打包、打印和司机真机闭环。
- PostgreSQL、对象存储、主数据导入和原材料入库真实验收。
- 对账、收款、附件和导出留档。
- 现场证据、角色签字和发布回滚。

### 本轮只做缺陷修复，不扩功能

- 排产自动插单、复杂换模和倒班引擎。
- 多笔/部分供应商付款、完整应付账龄和深度毛利经营分析。
- PDF/Office 在线预览和客户消息自动发送。

### 延后到 V2

- 售后责任分摊、绩效扣款和工资联动。
- 工资、考勤和完整人事管理。
- 企业微信会话存档、自动回复和客户群自动化。

## 七、验收红线

出现以下任一情况，不得宣布生产上线完成：

1. 代码只在本地通过，没有真实 PostgreSQL 或对象存储报告。
2. 打印只生成预览，没有真实出纸、对位、扫码和状态回读。
3. 司机端只在浏览器模拟，没有真实手机权限和原生能力验证。
4. 现场证据或负责人签字未完成。
5. 真实密钥、连接串、bucket、token 或设备路径进入 Git、JSON 或 Markdown 报告。
6. UI 重构后通过本地投影伪造后端写入成功。
7. 发布前没有回滚方案和远端可恢复代码基线。

## 八、每轮汇报格式

每轮代码或现场整改完成后，固定向项目负责人汇报：

1. 本轮修改了什么。
2. 解决了什么问题。
3. 哪些问题仍未解决。
4. 运行了哪些验证，结果是什么。
5. 当前门禁、证据和签字数字是否变化。
6. 下一轮建议做什么，以及需要谁配合。

任何百分比和“已完成”结论必须有代码、自动化、真实环境、设备或现场证据支撑。
