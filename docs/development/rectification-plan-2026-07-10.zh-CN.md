# ERP 系统整改实施方案

制定日期：2026-07-10
当前版本：V3（按六个批次、逐项门禁执行）

## 一、结论

当前代码属于高完成度 ERP 原型和 V1 候选实现，尚不能宣布生产上线完成。

- P0 原型代码完成度约 `97-98%`。
- V1 上线就绪度约 `80-83%`。
- 发布门禁仍为 `0/4`，现场证据 `0/34`，负责人签字 `0/6`。
- 批次 A 已完成代码整改和自动化验收；批次 B 已进入代码实施，但尚未通过完整验收，不能标记完成。
- 后续开发不再优先增加页面，先处理生产基础设施、设备和真实业务闭环。

## 二、整改原则

1. 先保证数据正确，再精简代码和重构 UI；不得用界面完成度代替业务闭环完成度。
2. 每个批次必须同时给出代码、自动化、真实环境和现场证据四类结论；没有执行的验证明确写“未验证”。
3. production 只认 PostgreSQL 和对象存储中的正式数据，不允许内存、本地 JSON 或浏览器状态成为成功依据。
4. 结构重构与业务规则修改分开提交；一次只移动一个领域边界，并用原有行为测试兜底。
5. 不迁移 `.erp-local-storage` 中的演示 / 测试业务数据；生产初始数据只来自审核后的导入模板。
6. 上线前冻结工资考勤、企微自动化、BI、高级毛利和其他 V2 扩展，避免稀释 V1 主链路。

## 三、主要问题

| 类别 | 审计结论 | 风险 |
| --- | --- | --- |
| 运行环境 | 过去 demo、测试和生产边界不够明确 | 测试数据可能进入演示目录，生产可能误用本地仓储 |
| 认证权限 | 前后端角色权限曾重复维护，办公室曾拥有全部 `system.v1_*` | 权限漂移，办公室可执行技术上线动作 |
| 生产持久化 | PostgreSQL、对象存储代码边界已存在，真实服务未验收 | 本地 JSON / 文件不能作为正式生产事实来源 |
| 设备集成 | 打印、CUPS、司机手机已有接口和检查器，未完成真实设备证据 | 预览或模拟成功不等于真实出纸、扫码、定位成功 |
| 代码结构 | `App.jsx`、办公室页面和 API 主入口仍然过大 | 修改成本高，回归范围大，UI 规则容易分叉 |
| UI 一致性 | 核心页面可用，但筛选、表格、侧栏、空态和错误态尚未完全统一 | 培训成本高，窄屏和异常状态容易遗漏 |
| 发布管理 | 本地 Git 基线已建立，远端恢复、现场证据和签字未完成 | 本机故障不可恢复，无法形成正式发布结论 |

## 五、批次 B：数据一致性、生产基础设施与部署基线

状态：`进行中；B1-B2 本地代码和 PostgreSQL 16 容器集成通过，B3-B5 未完成`

### B1：统一写入幂等和并发控制

当前结果：`代码完成，专项 / production HTTP / PostgreSQL 16 并发重放通过；真实生产环境待验收`

1. 所有 production 业务写请求必须携带 `idempotency-key`；同键同请求返回原结果，同键不同请求拒绝执行。
2. 幂等记录只保留请求摘要、响应、业务目标和有效期，不保存原始敏感请求。
3. 订单、库存、交付、对账单、原材料、打印和司机派送增加行锁或 `revision` 乐观锁。
4. 库存不足、旧版本写入和重复业务动作必须返回明确冲突，不能使用 `GREATEST(0)` 一类写法掩盖超扣。
5. 事务失败必须整体回滚；前端收到成功后再刷新服务端读模型。

验收：重复请求不产生重复订单、扣减、收款、核销、打印或派送；并发冲突可识别且数据库无部分写入。

### B2：六条核心写链事务化

当前结果：`订单、出库交付、收款核销、原材料、打印、司机派送首轮事务与回滚边界通过本地及 PostgreSQL 16 集成；现场数据试跑待完成`

| 写链 | 必须处于同一数据库事务的内容 |
| --- | --- |
| 订单确认 | 正式订单、明细、库存占用、库存流水、操作日志 |
| 出库交付 | 交付状态、库存释放 / 扣减、包裹 / 凭证关联、操作日志 |
| 收款核销 | 实收、差额、核销、对账单版本、金额审计 |
| 原材料 | 入库、卷 / 件标签、复核、机边领料、余料来源和状态 |
| 打印 | 作业、批次、重打 / 作废关系、设备与 spool 回写 |
| 司机 | 派送、装车、送达、异常和证据元数据 |

验收：六条写链均有 repository 直接测试、真实 PostgreSQL 集成测试和至少一条失败回滚用例。

### B3：生产数据库成为唯一事实源

当前结果：`未完成`。打印作业、打印设备、司机派单和原材料已能从 PostgreSQL 重载；订单草稿及部分订单 / 库存 / 交付 / 对账工作区仍需消除启动 seed / 旧快照依赖。

1. 禁止“先改内存工作区，再异步写库”；repository 必须返回数据库提交后的版本。
2. production 启动和页面刷新从 PostgreSQL 加载订单、库存、交付、对账、原材料、打印和司机状态。
3. API 响应包含必要的 `revision`；旧页面快照提交时由服务端拒绝并提示刷新。
4. 修复任何使用调用方旧数组覆盖数据库返回值的写后投影逻辑。

验收：重启 API、刷新浏览器或并发打开两个会话后，显示结果都与数据库一致。

### B4：真实 PostgreSQL、对象存储与迁移恢复

1. 在真实 PostgreSQL 执行迁移、checksum 校验、并发事务、备份和专用恢复验证库演练。
2. 在真实 OSS/S3/COS 验证附件上传、读回、短期签名访问、对账导出、删除、版本控制、生命周期和加密。
3. 迁移必须可重复执行；已执行迁移内容变化时必须阻断，不允许静默覆盖。
4. 恢复演练只使用专用可重置验证库，不能清理生产库。

验收：迁移、备份 / 恢复和对象存储报告均来自真实服务且保持脱敏。

### B5：远端恢复与部署运维

1. 配置受控 Git 远端，推送当前基线，并在全新目录完成 clone、安装、构建和恢复验证。
2. 在受控主机填写生产 env，真实值不得进入 Git、Markdown、JSON、截图或聊天记录。
3. 建立 API / Web 启停、日志、健康检查、备份、告警和回滚手册。
4. 为 V1 状态测试和上线产物增加独立 artifact root，消除读取上一次本地产物造成的测试顺序依赖。

退出条件：B1-B5 全部通过；生产 API 只能以 production 模式启动，全部实际仓储为 PostgreSQL / object storage，六条写链具备幂等、并发和回滚证明，代码与数据均可恢复。

## 十、优先级和执行顺序

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| P0 | B1-B3 数据幂等、并发、事务和唯一事实源 | 直接影响重复扣库存、重复收款和数据丢失 |
| P0 | B4-B5 真实基础设施、备份恢复和受控部署 | 决定系统能否从本机原型转为可恢复生产服务 |
| P0 | C-D 真实设备与真实业务试跑 | 模拟和预览不能证明工厂现场可用 |
| P1 | E 代码精简和 UI 重构 | 降低维护成本，但必须建立在稳定业务链路上 |
| P0 | F 证据、签字和灰度发布 | 未通过不得宣布上线 |

执行主线：

```text
A 已完成代码验收
→ B1 幂等/并发
→ B2 六条事务链
→ B3 PostgreSQL 唯一事实源
→ B4-B5 真实基础设施/恢复/部署
→ C 真实设备
→ D 真实业务试跑
→ E 结构与 UI 收口
→ F 证据/签字/灰度上线
```

## 十一、变更和回滚规则

1. 每个子阶段独立提交，提交信息必须说明业务范围；不得把无关格式化混入事务或权限修改。
2. 数据库迁移采用只追加策略，已发布迁移不得改写；修正通过新迁移完成。
3. 高风险写链发布前保留旧版本部署包和数据库备份；回滚代码前先判断新迁移是否向后兼容。
4. UI 重构必须保持 API 契约和业务状态机不变；出现回归时可按领域提交单独回退。
5. 任何真实值、附件内容、生产数据库快照和现场隐私资料都不能进入 Git 或普通报告。

## 十二、上线红线

出现以下任一情况，不得宣布上线完成：

1. production 可以使用本地内存、JSON 或本地文件作为正式事实来源。
2. 正式环境还能使用 seed 账号、身份 Header 或前端本地写入回退。
3. 办公室普通账号可以执行生产配置、持久化留证或发布候选刷新。
4. 打印只有预览，没有真实出纸、扫码和状态回读。
5. 司机端只有浏览器模拟，没有真实手机权限和证据。
6. PostgreSQL、对象存储、现场证据、签字或回滚演练未完成。
7. 真实密钥、连接串、bucket、token、命令或本机路径进入版本库和报告。

## 十三、每轮汇报格式

每轮整改完成后固定汇报：

1. 本轮修改了什么。
2. 解决了什么问题。
3. 哪些问题仍未解决。
4. 运行了哪些验证，结果是什么。
5. 门禁、证据、签字数字是否变化。
6. 下一轮建议和需要配合的负责人。

任何百分比和“已完成”结论必须有代码、自动化、真实环境、设备或现场证据支撑。
