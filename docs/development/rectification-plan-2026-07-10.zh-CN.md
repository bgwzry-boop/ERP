# ERP 系统整改实施方案

制定日期：2026-07-10
当前版本：V2（按六个批次执行）

## 一、结论

当前代码属于高完成度 ERP 原型和 V1 候选实现，尚不能宣布生产上线完成。

- P0 原型代码完成度约 `97-98%`。
- V1 上线就绪度约 `80-83%`。
- 发布门禁仍为 `0/4`，现场证据 `0/34`，负责人签字 `0/6`。
- 本轮批次 A 已完成代码整改和自动化验收，但真实生产配置、外部服务、实体设备和现场签字没有因此完成。
- 后续开发不再优先增加页面，先处理生产基础设施、设备和真实业务闭环。

## 二、主要问题

| 类别 | 审计结论 | 风险 |
| --- | --- | --- |
| 运行环境 | 过去 demo、测试和生产边界不够明确 | 测试数据可能进入演示目录，生产可能误用本地仓储 |
| 认证权限 | 前后端角色权限曾重复维护，办公室曾拥有全部 `system.v1_*` | 权限漂移，办公室可执行技术上线动作 |
| 生产持久化 | PostgreSQL、对象存储代码边界已存在，真实服务未验收 | 本地 JSON / 文件不能作为正式生产事实来源 |
| 设备集成 | 打印、CUPS、司机手机已有接口和检查器，未完成真实设备证据 | 预览或模拟成功不等于真实出纸、扫码、定位成功 |
| 代码结构 | `App.jsx`、办公室页面和 API 主入口仍然过大 | 修改成本高，回归范围大，UI 规则容易分叉 |
| UI 一致性 | 核心页面可用，但筛选、表格、侧栏、空态和错误态尚未完全统一 | 培训成本高，窄屏和异常状态容易遗漏 |
| 发布管理 | 本地 Git 基线已建立，远端恢复、现场证据和签字未完成 | 本机故障不可恢复，无法形成正式发布结论 |

## 三、批次 A：运行模式、权限和生产失败关闭

状态：`代码完成，自动化通过，生产部署待验收`

已完成：

1. 新增 `demo`、`test`、`production` 三种显式运行模式。
2. 默认本地数据按运行模式隔离；显式测试目录继续优先，避免破坏现有专项测试。
3. 新增仅允许清理 demo 分区的一键重置工具，test / production 分区不能被该工具删除。
4. production 强制 PostgreSQL、对象存储和严格认证；缺数据库、对象存储或实际仓储类型不符时拒绝启动。
5. production 禁止 seed 登录、旧 `x-erp-user-id` 身份 Header 和前端本地写入回退，只允许正式账号登录。
6. 前后端改为共用一个角色权限目录，消除两套权限表。
7. 办公室角色移除全部 `system.v1_*`；管理和新增技术运维角色可执行上线技术动作。
8. 生产 env 预检新增 `ERP_RUNTIME_MODE=production`，上线预检从 10 项更新为 11 项。
9. 新增运行模式、权限目录和办公室拒绝用例，并纳入核心测试链。

验收结果：

- `npm test` 通过。
- `npm run batch-a:check` 通过。
- 生产 env、发布候选、上线套件、真实值 intake 和第一阶段执行专项通过。
- 生产构建通过。
- 生产登录页在 1280×720 和 390×844 下无页面横向溢出，应用控制台错误为 0。

批次 A 不代表以下事项已完成：真实 PostgreSQL、真实对象存储、生产账号导入、生产域名/CORS、正式密钥轮换和受控主机部署。

## 四、批次 B：生产基础设施与部署基线

状态：`下一批`

工作项：

1. 配置受控 Git 远端，推送当前基线，并在全新目录完成 clone、安装、构建和恢复验证。
2. 在受控主机填写生产 env，真实值不得进入 Git、Markdown、JSON、截图或聊天记录。
3. 在真实 PostgreSQL 执行迁移、并发事务、备份和专用恢复验证库演练。
4. 在真实 OSS/S3/COS 验证附件上传、读回、签名访问、对账导出、保留策略、版本控制和加密。
5. 建立 API / Web 启停、日志、健康检查、备份、告警和回滚手册。
6. 为 V1 状态测试和上线产物增加独立 artifact root，消除读取上一次本地产物造成的测试顺序依赖。

退出条件：生产 API 只能以 production 模式启动，全部实际仓储为 PostgreSQL / object storage，真实基础设施报告可追溯，代码可以从远端恢复。

## 七、批次 E：代码精简和 UI 重构

状态：`持续进行，业务试跑稳定后集中收口`

代码整改：

1. `App.jsx` 继续拆为应用壳、页面控制器 hooks、共享弹窗和领域状态模块。
2. `src/pages/office/index.jsx` 按待办、订单、库存、交付、对账、生产、原材料和基础资料拆分。
3. `server/apiServer.mjs` 只保留启动、公共中间件、仓储装配和路由装配；业务进入 service/domain。
4. 共用表格筛选、分页、状态映射、详情侧栏和请求状态组件，删除重复映射和重复权限判断。
5. 每次只拆一个可独立验证的边界，不在结构重构中同时修改业务状态机。

UI 整改：

1. 保持高密度 ERP 工作台、窄侧栏和紧凑表格，不改成营销页或大卡片看板。
2. 统一页面标题栏、筛选区、表格列密度、状态色、详情侧栏、加载态、空态和错误态。
3. 订单录入继续保留上方大文本识别区、表格行内编辑和复杂印刷侧栏。
4. 统一库存状态：可用绿色、占用黄色、缺货红色、待处理灰色。
5. 验证 1280、1440、1920 和 390px，不允许文字、按钮、表格和侧栏无意义重叠。

退出条件：核心页面前后行为一致，权限不回退，关键状态模块有直接测试，浏览器无错误和布局溢出。

## 九、上线红线

出现以下任一情况，不得宣布上线完成：

1. production 可以使用本地内存、JSON 或本地文件作为正式事实来源。
2. 正式环境还能使用 seed 账号、身份 Header 或前端本地写入回退。
3. 办公室普通账号可以执行生产配置、持久化留证或发布候选刷新。
4. 打印只有预览，没有真实出纸、扫码和状态回读。
5. 司机端只有浏览器模拟，没有真实手机权限和证据。
6. PostgreSQL、对象存储、现场证据、签字或回滚演练未完成。
7. 真实密钥、连接串、bucket、token、命令或本机路径进入版本库和报告。

## 十、每轮汇报格式

每轮整改完成后固定汇报：

1. 本轮修改了什么。
2. 解决了什么问题。
3. 哪些问题仍未解决。
4. 运行了哪些验证，结果是什么。
5. 门禁、证据、签字数字是否变化。
6. 下一轮建议和需要配合的负责人。

任何百分比和“已完成”结论必须有代码、自动化、真实环境、设备或现场证据支撑。
