# 当前规则：发布、权限与服务安全

从根 AGENTS.md 按业务域进入。本文件保留已记录决策的原文；跨域修改须同时查阅相关规则。当前完整桌面采用八组业务导航，历史五域及分离价格表方案不再是当前入口。

- The desktop review topbar begins directly with global search. Do not place a fixed factory-name label such as `虎门工厂` between the sidebar brand and search: the brand and current workbench already establish context, while the repeated label wastes scan space. If multi-factory switching becomes real later, introduce an explicit permissioned factory selector rather than restoring static text.

- The independent PC review prototype does not use one universal four-column KPI strip beneath every workbench heading. The repeated `business-metrics` row was rejected on 2026-08-01 because it forces unrelated pages into the same dashboard template and repeats list facts. Keep the record count and refresh in the workbench heading; keep state filters or internal-area tabs only when they operate the current list. Page-specific totals may appear only where the deployed PC page or an explicit business decision requires them, never as a decorative equal-width row.

- Supplier-paper colour is OCR evidence, not the final factory colour authority. Delivery-note review shows the recognized supplier wording beside an explicit factory-standard-colour selector; only a value from the maintained canonical factory palette may pass review. The selected factory colour is carried by the roll code record, label, inventory and downstream issue flow, while the original supplier colour remains immutable audit evidence. Return review preserves supplier wording and does not require inventing a new factory colour for material leaving the factory.

- The flow-atlas `第 7 卷` handle-strip example opens with the specification field prefilled as `65克*5宽`, the empty-field blocker is not shown, and the state is `待确认`. Because the supplier/OCR source says only `条`, the handle-strip default is applied and no meter length is invented; if a real meter length is recognized it is appended. The supplier/OCR source remains `条` in the collapsed evidence and must not be overwritten; the normalized value becomes authoritative only after the worker taps `这卷正确`.

- Public Todo is an office desktop workbench with count-bearing state shortcuts, page-scoped query/business filters, a dense todo/customer/summary/due/rule/status/reference list, and an independently scrolling detail area. Server sorting, reminder escalation, batch-print trust, reference repair, and deep-link validation remain authoritative.

- Operational copy must earn visible space. Do not repeat the page title, role identity, workflow steps, current status, or next action in explanatory prose. Default screens keep only business facts, blockers, evidence needed for the current decision, and one concise next-action instruction; history, authority detail, environment/source detail, and secondary explanations belong behind progressive disclosure or at the exact confirmation/error boundary where they matter. Prototype `seed`/API/fallback explanations must not occupy normal worker surfaces, and a disabled control should carry a short actionable label instead of a persistent paragraph. New-user guidance is not permission to add always-visible tutorial copy.

- Mobile business-decision evidence screens never restate a signal from the dominant summary in a separate information card. Distinct operational details may be folded into the nearest compact checklist, but generic reminders such as `决定前 / 看完事实和证据` are omitted. High-risk confirmation screens intentionally repeat the complete decision snapshot before submission; result screens present the authoritative outcome once inside the result block and use a neutral scope title without a second `已记录 / 已生效` badge.

- V1 role tools that are already implemented must appear after the six P0 office pages in a permission-scoped secondary navigation group; internal enum values such as `pickup`, `delivery`, and `express_ltl` must be converted to Chinese labels at the API/UI boundary and must not appear in visible operational tables.

- Shared mobile confirmation components fail closed. Interactive checklists start entirely unchecked, expose `aria-pressed`, and block the primary action until every required item is confirmed; explanatory or system-calculated lists are read-only numbered facts and never look pre-completed. Required photos or attachments have visible idle, saved, failed, retry, and retake states, and the primary write remains disabled until server-accepted evidence exists. Every high-risk confirmation keeps an explicit `返回修改 / 取消提交` action; a renderer must never hide it because its label begins with `返回`.

- Inventory Query is an office-operated desktop workbench. Its durable layout uses count-bearing stock shortcuts, compact page-scoped keyword/specification filters, a dense specification/quantity list, explicit text state/trust labels, prominent available/in-stock quantities, and an independently scrolling detail pane; temporary holds, inventory ledgers, and correction workflows retain their server-authoritative contracts.

- Missing or unverifiable todo references may be repaired only through an explicit authenticated office action on an unhandled todo. The server must validate the new target, require a reason, atomically persist the new reference plus event and operation log, preserve before/after evidence, and fail closed when the target is invalid; a valid existing reference is never silently rewritten.

- Every newly created todo must pass the same server-owned target resolution and semantic type checks before its business transaction starts. Unsupported, missing, or incompatible targets fail closed instead of relying on later list-time repair.

- Delegated business-decision evidence uses a server-created draft fixed to one business type, business ID, and decision scope. Office A/B may hand off the same pending draft only when both have the relevant business permission; attachments are uploaded as real files/photos to that draft and users never type attachment IDs. Formal business submission must lock and revalidate the draft and attachments, create the decision and links, consume the draft once, execute the business write, and record the audit log in one transaction; any failure rolls back consumption. Historical views show filenames and use the permissioned content endpoint, never storage paths or signing details.
