# 当前规则：人员、考勤与工资

从根 AGENTS.md 按业务域进入。本文件保留已记录决策的原文；跨域修改须同时查阅相关规则。当前完整桌面采用八组业务导航，历史五域及分离价格表方案不再是当前入口。

- Desktop `基础资料 → 员工机台` uses the main list for operational scanning only: `序号 / 员工 / 岗位 / 车间 / 机台 / 状态`. `序号` is the stable one-based position in the current authoritative employee roster and stays narrow; the employee name remains the primary row identity and the selected-detail title. The login `账号` does not occupy a repeated list column; it appears in the selected employee's right-side detail together with the employee number and remains searchable as hidden metadata. Account lifecycle actions continue to use the server-authoritative employee-account flow.

- ERP account and permission rollout follows Taobao-style subaccounts. The owner resumed implementation on 2026-08-25: an authorized `permission.manage` administrator can create a distinct subaccount, optionally bind it to one employee, assign one or more reviewed role bundles, and apply audited per-permission allow/deny exceptions. New subaccounts remain login-disabled until a separate one-time temporary-password action; suspension, reactivation and permanent disablement invalidate existing sessions, optimistic permission revisions prevent stale overwrites, and the temporary password must never persist in or reappear from the user list. Employee profile, operational role, workshop/machine assignment and payroll position remain separate facts; creating or importing an employee must never automatically create an account, enable login, or infer permissions from payroll/role labels. The current implementation governs functional permissions only; do not present workshop/customer/warehouse row-level data scope as enforced until each underlying read/write query consumes a server-authoritative scope contract. The capability does not authorize bulk creation or enablement: real accounts are created only through an explicit administrator action for an accepted person.

- The owner explicitly rejected a technical permission-table UI as too difficult to understand. The default administrator experience under `基础资料 → 员工机台 → 岗位分配` is person-first and position-first: select the subaccount, click one or more visual position cards such as `办公室 / 库房 / 财务 / 司机 / 车间 / 打包`, review short written business scopes, and save. The server still derives and audits the exact permission bundles and preserves any existing allow/deny exceptions, but raw permission keys and per-key dropdowns stay out of the everyday position-assignment flow.

- Desktop `基础资料 → 员工机台` selected detail groups personnel information as `员工档案 / 工作安排 / 账号信息`. `员工档案` includes employee number, name, age, entry date, factory tenure, and employment status; `工作安排` includes role, workshop, current machine, and notes. Age is derived from the maintained birth date and factory tenure is derived from the maintained entry date, so neither drifting value is stored or invented. Missing dates display `未维护 / 待维护入职日期`; future payroll seniority-award calculation must reuse this same authoritative entry date and tenure rule rather than introducing a second manual seniority value.

- Attendance and payroll link through the stable ERP employee number, never through a mutable name. Deli, Enterprise WeChat, or a replacement attendance provider keeps its person identifier as an external identity mapping; immutable raw punch events resolve through that mapping to the ERP employee, reviewed minute-level work segments, and the employee/month payroll draft. `员工机台` may show a compact attendance/payroll entry point, while accountant-wide calculation and review live in the independent `财务管理 → 工资核算` workbench. The employee phone `我的考勤` view exposes only that logged-in employee's punch timestamps, daily hours, current-month confirmed hours, attendance exceptions, and `截至今日` estimated pay. Employees cannot see coworkers or edit raw punches; they may submit an explanation for HR review. Running estimates must state that unresolved attendance is excluded and that the amount is not final payroll.

- Basic wage is defined by payroll position, not repeated on every employee. A stable `payrollPositionKey` is independent from permission role, workshop and machine assignment; each employee links to one effective payroll position, while the versioned payroll policy owns that position's explicit calculation mode, rate composition and effective period. Hourly positions use base hourly wage plus hourly position allowance; the supplied driver position uses a separate daily wage and must never be coerced into an invented hourly rate. A payroll draft snapshots the resolved position/rate version for audit. Performance awards, leave deductions and other employee-specific adjustments remain line-level accountant actions with written basis and evidence; they never become a hidden personal base wage. Until the formal position-rate contract and approved values are deployed, current per-employee wage fields are legacy intake data only and must not be represented as the final wage authority.

- The currently enabled single employee account is the accepted functional pilot scope for employee self-service, attendance visibility and payroll permission testing. The other active accounts stay pending administrator review until the owner supplies and accepts their personnel data. A one-person pilot never satisfies formal whole-factory payroll readiness and must not be reported as production attendance/payroll acceptance.

The current punch machine is not assumed to expose a usable API, so `ERP_ATTENDANCE_PROVIDER_MODE` remains absent or explicitly disabled during the one-person functional pilot; this is a visible non-blocking warning for the approved raw-material-first rollout, while formal payroll readiness stays blocked. - A newly configured attendance provider is checked through the server-side read-only sync precheck before the first formal import. The precheck may call the configured gateway for an explicit time range, but it writes no batch or punch data and returns only aggregate validity, duplicate, mapping-coverage and already-imported/new counts. It never returns ERP employee identities, provider person IDs, punch IDs, raw payloads or tokens. The actual write endpoint fetches and assesses the source again; any invalid or out-of-range timestamp/date, duplicate punch identifier, unmatched/ambiguous mapping, or incomplete active-employee mapping aborts the whole import before a batch or punch is persisted. Precheck success does not satisfy payroll readiness.

- Payroll performance awards, leave/absence deductions, and other deductions are explicit accountant-entered values on a `工资草稿`; they are never inferred from an after-sales clue or silently applied to pay. Every amount-changing adjustment requires a written basis plus at least one authenticated business-owned image/PDF attachment and saves immutable before/after values, evidence IDs, operator, and time. Only `draft` lines may change; after accountant review, any correction requires a newly generated payroll revision. Employee history follows the stable ERP employee number even after departure, while CSV export is bound to one exact payroll-run revision and carries a server-generated SHA-256 digest. These code capabilities do not authorize production payroll until the real attendance endpoint, employee-to-payroll-position links, approved position-rate policy values, permissions, database migration, and acceptance evidence are configured.

- Payroll draft creation and status changes are optimistic, database-enforced accounting transitions. A new draft revision is accepted only when it immediately follows the persisted latest revision for that payroll month; concurrent requests converge on one row and all stale attempts return an explicit conflict. Manual line adjustments compare the persisted prior performance/leave/other values before updating, so concurrent edits cannot silently overwrite one another. Review, lock and payment are exact forward transitions `draft → reviewed → locked → paid`; they never rewrite payroll lines, and the first persisted reviewer/locker/payer, timestamps and payment reference cannot be replaced by a stale request. PostgreSQL guards keep run identity/generation evidence immutable and allow line insert/update/delete only while the parent run is `draft`.

- Formal payroll CSV export is a sensitive write-like action, not an ordinary payroll preview. Only finance/management accounts with the explicit `payroll.export` permission may export, and only a `reviewed / locked / paid` run may produce a formal file. Every successful export writes an immutable digest-only audit event containing the exact run/revision/status, safe filename, SHA-256 content digest, row count, operator and server time; it never duplicates wage rows in the audit table. The insert compares the current persisted run snapshot, so a concurrent state transition yields `PAYROLL_EXPORT_SNAPSHOT_CONFLICT` rather than recording ambiguous evidence. Draft exports remain blocked.

- Attendance-day rejection means `暂不计薪`, not `待复核`. A rejected anomaly keeps the original immutable punch evidence and raw paired minutes for audit, resolves the pending-review blocker, and forces the confirmed/payroll work minutes for that day to exactly zero. It must never silently restore raw minutes or remain permanently pending after an authorized review.

- Payroll-policy input fails closed instead of repairing questionable finance rules silently. Standard daily minutes and overtime multiplier must be valid explicit numbers; every seniority-award tier requires a unique integer service-year threshold and a bounded nonnegative monthly amount. Every payroll-position rate requires a unique stable key, written position name and explicit `hourly / daily` calculation mode: hourly mode requires a positive base hourly wage and bounded nonnegative hourly position allowance; daily mode requires a positive daily wage and rejects hourly-rate fields. The authenticated server operator and server clock own creator/reviewer/time evidence, regardless of client fields. A new version must first persist as `draft`; the same returned version id may then publish, while a first request that tries to create `published` fails with `PAYROLL_POLICY_DRAFT_REQUIRED`. A published or retired policy version is immutable in both local and PostgreSQL paths; a changed rule always receives a new version and integrity digest, and the same effective date cannot publish twice.

- Formal payroll readiness is a non-mutating, fail-closed server check for one selected payroll month. Payroll follows the China factory natural month: a formal draft may be generated only after that month ends, normally during the following month's `1–5` review window. Readiness requires PostgreSQL persistence, a configured real attendance source, at least one active employee, complete profile dates, complete employee-to-payroll-position and attendance mappings, one matching rate for every used position in the published month-effective payroll policy, and one or more successful zero-unmatched import ranges whose clipped union continuously covers the exact factory-local interval from the selected month's first day `00:00 +08:00` to the next month's first day `00:00 +08:00`. It also requires zero pending attendance reviews and enabled employee self-service accounts that have completed their mandatory password change. The projection returns counts and criterion states only; it never exposes employee identities, attendance tokens, or connection strings. Every human operational role may read only its own attendance, while coworker attendance and payroll workbenches remain finance/management permissions. A successful read-only precheck, a partial-month import, a future-ended request made before period close, an import from another month or the one-person pilot never authorizes a formal payroll draft. Draft generation additionally requires every employee in the run to have at least one confirmed attendance day in the selected month; an employee with no linked punch cannot receive an estimated seniority award or a zero-hour payroll line and instead remains explicitly blocked for attendance review.

- `attendancePayrollRepository` is a first-class production persistence store and must remain in the system V1 persistence catalog alongside the other finance repositories. Production readiness must fail closed unless it reports `postgres`; a payroll-specific readiness check may not substitute for the system-wide repository inventory, and adding another formal repository requires updating both the persistence option profile and the system catalog so their counts cannot drift.
