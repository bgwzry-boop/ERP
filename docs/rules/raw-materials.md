# 当前规则：原材料与厂家票据

从根 AGENTS.md 按业务域进入。本文件保留已记录决策的原文；跨域修改须同时查阅相关规则。当前完整桌面采用八组业务导航，历史五域及分离价格表方案不再是当前入口。

- 原材料手机拍单默认按一页保持轻量，但拍完第一页后必须提供明确的“没有第二页，开始识别 / 还有第二页，继续拍”分支；同一张厂家送货单最多按顺序附加 4 页并作为一个入库草稿、一个单号和一组汇总一起识别复核，不能把少见的两页单据默认为两张独立单据，也不能事后仅凭供应商或单号自动合并已经建立的草稿。每页原图分别作为不可替代的审计附件保存，OCR 表格和每条明细保留 `sourcePageIndex`，手机逐行核对与放大原图必须切到该行真实来源页。分页页小计不得冒充全单汇总；整单明细、总重量和声明金额不一致时继续显式阻断人工复核。厂家表头的 `编号 / 商品全名` 出现 `57 / 号 / 空白` 等轻微 OCR 漂移时，只要 `规格 / 单位 / 数量 / 单价 / 金额` 的业务列仍完整，就按厂家逐卷版式恢复解析，禁止因首列表头漂移而丢弃整页。

- 原材料手机拍单选择或拍摄页面后，必须立即显示按顺序排列的逐页缩略预览、明确页码，并允许在开始识别前查看大图或删除单页；预览使用 OCR 副本以控制手机内存，正式审计仍保存每页未经替代的原图。同一张单有多页时，界面需明确提醒全部添加后再识别，不能只用“已拍 N 页”的文字替代视觉核对。

- 原材料颜色必须同时保留“厂家票面颜色”和“厂内标准色”，不能假设不同供应商对同一实物使用相同叫法。后台按供应商维护可修改、可停用且有操作审计的 `厂家票面颜色 → 厂内标准色` 映射；OCR 先保留票面原文，再按当前供应商规则优先换算，之后才允许使用全厂通用别名。未匹配或同一厂家规则冲突时必须阻断并人工选择厂内标准色；一次人工核对不得静默学习或改写映射，只有有权限的后台维护动作才能更新规则。

- 工厂标准色的首批权威来源是【下单小程序】中已提交的横款/竖款袋子实拍：图片文件名与结构化袋身/提手字段共同确认单一布料颜色。`焦糖米提 / 白黑提 / 粉袋酒红提` 等是成品配色组合，必须拆成袋身色和提手色，组合名本身不得进入卷料标准色。当前首批为 `shared/factoryStandardColors.js` 中 35 个有实拍证据的标准色；工厂已明确确认不存在 `云雅绿 / 天池蓝 / 梦幻紫`，任何色卡、导入、OCR 或映射都不得把它们作为厂内标准色或普通候选色。历史 `本白 / 大红 / 宝兰 / 天兰 / 桔红` 作为明确兼容别名分别归一到 `白色 / 红色 / 宝蓝 / 天蓝 / 橘色`，新厂家叫法仍必须走有审计的供应商专属映射，不能凭相似颜色静默合并。

- 原材料手机 OCR 复核不得再用固定厂内颜色下拉框要求逐卷手选。已命中厂家规则时直接显示 `厂家票面颜色 → 厂内标准色` 自动换算结果；首次新叫法或规则冲突进入一次性的有权限规则维护，允许从已有厂内标准色选择或显式新建标准色，保存后立即回填当前单据中同一票面颜色，并供以后同厂家自动换算。

- 原材料手机 OCR 核对页的返回不能只是退出页面并遗留后台草稿。对仍处于 `已识别待复核` 的单据，必须明确提供 `放弃这张，重新拍 / 继续核对 / 保留草稿，返回首页`：放弃复用有权限且有审计的作废动作，服务端确认 `已作废` 后才返回拍单首页；已作废草稿不进入正常入库、手机未完成、搜索、统计或供应商对账列表，也不形成库存、应付或对账数据，但原图、作废人、时间和原因继续保留用于审计。

- Desktop `原料管理 → 卷料库存` is scanned and paged by authoritative numeric width, not by the roll trace code or incidental API order. The first list column is `规格（宽幅）`: width is the primary value and the complete material specification is secondary; numeric widths sort ascending and missing/unconfirmed widths remain last. The width filter and available-stock distribution reuse the same dynamic width order. The stable roll code remains a searchable/scannable trace key, appears compactly in the final list column with the full value retained in detail, labels and tooltips, and must never be renumbered merely to change presentation order. New OCR rolls keep the canonical `RM-<inbound identity>-<two-digit physical-roll sequence>` rule, while historical/manual and split-roll identifiers remain compatible so existing barcode and traceability relationships are not broken.

- Desktop `原料管理 → 卷料库存` contains only real warehouse states: exact `可用`, actual machine-side issue/consumption, and explicit roll-level `inventoryStatus = 余料待复核`. A newly recognized receipt whose inbound status is `已识别待复核` or whose roll label is merely `待人工复核` remains only in `收货录入`; it must never be reclassified as leftover inventory or appear in the physical-roll ledger before review completes.

- Finished-goods inventory reuses the raw-material roll-inventory colour language instead of rendering bag colour as plain text. Every concrete finished-goods colour is shown as the same square factory-colour swatch plus the written colour name in the inventory row, selected-detail heading, and `袋身 / 提手` fact. The swatch is a shared component and colour map consumed by both roll inventory and finished-goods inventory; it never replaces the written label. The Miniapp-photo-derived names in `shared/factoryStandardColors.js` are the canonical factory tokens; historical `大红 / 宝兰 / 本白 / 天兰 / 桔红` remain input aliases rather than separate swatch identities. `米白` retains its explicit swatch, while a future laminated colour such as `金色` requires its own accepted photo/master-data evidence before becoming a standard colour.

- The independent PC review prototype uses the left rail as its only page-level navigator. It does not use a full-width `当前位置 / 一级域 > 当前页` breadcrumb strip or repeat left-nav destinations as content-top switchers; this applies to raw-material destinations, production/packing/printing workbenches, and base-data pages. The left-navigation active item establishes location, while the workbench's own title establishes the current task. Put refresh and page-local actions in the workbench heading. Keep tabs only for state filters, real workflow steps, detail subviews, or internal areas that have no separate left-nav destination.

- The current `评估旧 ERP 出入库功能` PC review version is approved as the desktop experience baseline. Mobile adaptation must reuse the already approved `docs/prototypes/mobile-role-flow-atlas` phone flows and the formal `RawMaterialMobileOcrReview` implementation refined in the `修复识别条能力问题` task; do not redesign or rebuild those phone screens. Treat the `4174` raw-material review prototype's local `App.jsx` recognition state as presentation-only demo logic: it must never replace the formal supplier-aware OCR parser, row-level `sourceBounds`/`ocrAngle` evidence crop, return-direction safeguards, server save/revision handling, or existing phone workflow. Adaptation means connecting the current PC workbench to those existing mobile routes, components, contracts, and responsive boundaries while preserving their tested behavior.

- Shop-floor execution follows the actual device available to each role rather than assuming every onsite worker has a computer or the same phone workflow. Silk-screen workers, bag-making workers, packers, finished-goods warehouse workers, drivers, and onsite technical/maintenance workers use dedicated phone role pages and do not depend on PC terminals. Raw-material handling is performed by general workers and, when applicable, printing workers through permission-scoped phone scanning/registration; they do not use a PC for that flow. Office desktop workbenches remain the complete dispatch, data-entry, oversight, trusted-printing, and device-administration surfaces, and office A/B can see and coordinate all onsite task queues. Any mobile page must use a dedicated role shell and must not be a desktop left-nav/right-detail layout squeezed into a phone viewport. Platform deployment/ERP operations is not the same role as an onsite technical/maintenance worker and must not imply another factory computer.

- The first production rollout is intentionally raw-material-only. Build the office surface around delivery-note photo/PDF OCR, line-by-line human verification, one scannable label per physical roll, manual label-to-roll verification, and supplier Excel reconciliation at month end. Build the raw-material handler surface as a personal-phone scanner flow: the general worker or printing worker who physically takes a roll signs in with their own ERP account, scans that one available roll with the phone camera, records the destination machine/area, and moves it to machine-side issue. A shared PDA fleet is not an accepted operating dependency because several general and printing workers need concurrent access and dedicated devices would be costly, easily lost, and easily damaged. Every roll remains an independent authenticated server action; a coworker's account, a shared anonymous identity, a client-only success screen, or one scan that silently issues several rolls is forbidden. During this first rollout, raw-material issue must not require or fabricate an order or production-task link; the roll code itself carries color, specification, width, weight, supplier, and inbound traceability so workers no longer hand-copy those facts. Other ERP domains remain hidden in the production frontend through the explicit first-release build flag, while their code remains available for continued development.

- 原材料收货长期保留两条并行入口并汇入同一个服务端流程，不能因办公室设备上线而取消或降级手机线。办公室固定设备线可作为高频主路径：操作员把厂家送货单逐页平放在截图所示的台式高拍仪/文档扫描设备下，高拍仪负责拍摄录入而不是扫描卷标条码；ERP保存每页原图并交给现有腾讯云表格 OCR、供应商版式解析、厂家票面颜色映射和人工复核。设备随附的本地 OCR 只能辅助预览，不能成为库存事实或替代 ERP OCR/复核；高拍仪不得对送货单使用“去除手写/擦除笔迹”模式，因为手写重量、颜色和补充说明都是必须保留的业务证据。办公室确认 OCR 逐卷结果后，四英寸快递面单/标签打印机立即按物理卷记录逐张打印卷标，操作员拿着这些标签到原料现场，按重量、颜色和规格与实物卷一一匹配并贴标；办公室固定链不要求另配快递驿站式条码扫码枪。打印机必须支持当前卷标实际宽度、标签间隙或黑标校准、Windows 打印驱动及受控打印链，并以通过真机防水、防油污、摩擦、热、日照、粘贴和后续扫码测试的防水合成热敏标签或热转印材料为准；“防水快递面单纸”宣传和普通纸质热敏面单都不能直接视为验收通过。进入可用库存仍必须完成有权限操作员对每张标签和正确实物卷的逐卷贴标核对，但该核对不强制必须使用手机扫码。现有手机 `拍单 → 核对 → 打印 → 贴标` 和现场卷码扫码/领料路径完整保留，适用于到货现场、办公室设备不可用和机边领料；办公室线与手机线必须复用同一入库单、逐页附件、OCR job/revision、物理卷记录、卷码、标签版本、权限、去重、状态迁移和审计，禁止生成两套草稿或两套库存。

- Raw-material mobile workflow icons must match the action labels consistently across the progress strip, all-functions view, and current action. Use the camera for `拍单`, check-circle for `核对`, printer for `打印`, and a single-label tag for `贴标`; avoid the overlapping-tags glyph because it is visually ambiguous at the required 600px preview width.

- Raw-material phone specifications use one explicit display order throughout capture review, editing, label preview, physical attachment, scanning, and issue: `克重*宽度*米数`, for example `78克*70宽*2000米`. Supplier strings may place the authoritative current 78 GSM value in either of the first two positions; normalize only the display order, preserve the supplier/OCR wording in its disclosure, and never change or guess numeric values when the roles are ambiguous.

- Raw-material OCR failures around handle strips are row-specific, not document-wide: ordinary rolls in the same delivery note continue through normal recognition, while complete three-part specifications containing a confirmed `5cm` width (for example `65*5*1500` or the explicitly written legacy-compatible `78*5*1500 / 5*78*1500`) must be parsed as `提手条` without showing `规格没看清`. The factory-authoritative handle-strip defaults are `65克 / 5cm宽`, while body fabric defaults to `78克`; a supplier value that only says `条`, `条料`, `提手条`, or combines the category with a color applies the handle-strip defaults and enters the direct confirmation path. If the supplier explicitly writes another handle-strip GSM, preserve that explicit value instead of overwriting it with the default. Meter length is optional evidence: preserve and display the actual value when OCR recognizes it, but keep it absent when the supplier did not write it—never invent `1500米`, show `米数待补`, or block confirmation/save. Preserve the supplier wording as audit evidence, and never mark every roll in the note as failed because one strip row is exceptional.

- Raw-material OCR uses supplier profiles instead of one global table/spec rule. Current aliases and layouts are: `人意无纺布销售单 / 振恒` is one profile, with specification before colour, ordinary fabric width sometimes written as `1米`/100cm (OCR may reduce it to `1`), handle-strip specification blank, and printed price retained only as source evidence because it is not the authoritative actual price; `宁晋县达翔塑料制品有限公司 / 北陈 / 河北北陈无纺布有限公司` is one profile, with specification after colour, ordinary two-digit centimetre widths, and handle strip written as `0.05`; `宁晋县腾胜无纺布有限公司 / 腾胜` is one profile, with specification after colour, ordinary two-digit centimetre widths, and handle strip written as `条`; `河北宏尚无纺布有限公司 / 白候` is one profile, with ordinary two-digit centimetre widths, specification before colour, and handle strip written as `条`; `新乐市鑫隆宏无纺布有限公司 / 鑫隆宏` is a provisional profile whose name/spec may share one cell, ordinary width may be written as `0.X` metres, paper quality is often poor with handwritten additions, and handle strip is written as the required colour plus `纯料5公分`. Keep unconfirmed Xinlonghong cases review-blocked until real samples define the remaining layout; never generalize a supplier adapter to other factories.

- Supplier-return OCR is a separate signed document direction. An explicit `退货单 / 退料单`, negative material rows, or the supplier-profile return grammar identifies it. For `人意/振恒`, `退带色条` means a returned handle strip and `退带色布` means returned fabric; for `宏尚/白候`, the product marker `条` or `布` carries the return category while the colour cell may contain an actual returned colour, `废布`, or `彩布`. `宏尚/白候` fabric returns must retain an explicit pricing category `黑白布 / 彩布 / 废布`: black or white source wording maps to `黑白布`, colour wording maps to `彩布`, and an unresolved category blocks review because black-white and colour fabric may use different unit prices. Every returned physical-item weight, line total, document total, and amount retains the negative business direction; an explicit return title with positive printed magnitudes is normalized to negative signed facts. Missing return specification or meter length stays absent and does not block return review. If a still-pending older OCR draft was captured as delivery but its saved title/rows contain strong return evidence, the phone review must offer an explicit audited `改为退货单核对` action that reparses the persisted OCR table with the selected supplier-return direction, without another cloud OCR request; it must never silently mutate the client record or rewrite a reviewed/labelled/inventory record. A reviewed return is terminal as `退货单已复核` for inbound handling: it creates no inbound roll IDs, labels, printable rows, or available inventory, but it must create or match exactly one current-period negative supplier-reconciliation fact. The reconciliation fact retains the original attachment ID, document number/date, OCR text, reviewed values, and line crop bounds so finance can reopen the original return note. A supplier Excel return row matching the same ERP return links to that fact and must never deduct it twice. A physical stock return remains a separate explicitly linked outbound flow: scan the existing roll into `供应商退货暂存区`, confirm `已退厂`, and reduce inventory exactly once; merely reviewing a paper return note never changes stock.

- Supplier-return mobile review reuses the approved `核对送货单` page anatomy, tokens, density, and interactions exactly: the same office role bar, back/title heading, progress component, real document card, continuous physical-item ledger, per-item horizontal source crop, compact facts/status/action row, and sticky two-action footer. Only return-specific facts and terminal wording change. The return page must not introduce a parallel independent-review shell, explanatory side column, oversized rule cards, or large form-style roll cards. Its terminal action is `确认退货`, never `进入打印`; completion still creates no label or available inventory.

- Supplier-return detail ownership is `原料管理 → 收货录入 → 退货单`. That workbench is the authoritative operational ledger for the original image, signed negative line facts, supplier, document number/date, amount and human review history. `财务管理 → 供应商月结` shows only the resulting negative reconciliation/credit summary and links back to the source return; `原料管理 → 卷料库存` shows only any separately confirmed physical stock effect. A paper return must not be made discoverable primarily through monthly settlement or by inventing an inbound roll row.

- Office raw-material roll labels use one shared cross-site grammar for ERP receiving and the future in-house raw-material factory: `供应商 → 本卷重量 → 颜色 · 克重*宽度*米数 → 全宽 Code 39 → 可人工输入的卷码`. Do not print the generic heading `原材料卷标` inside the label because the print-step context and the label's business facts already establish its type. The machine-readable code encodes only the canonical roll ID, keeps explicit quiet zones, and never packs mutable facts such as colour, specification, or weight into the barcode. Upstream production, ERP receiving, and mobile preview must reuse the same identifier, barcode builder, and label anatomy rather than maintaining separate label languages. Do not use fake CSS/QR patterns; production adoption still requires physical printer and scanner acceptance.

- Office raw-material printing must read the confirmed physical-roll ledger from `核对送货单` directly. The print and print-complete pages list every roll with `第 N 卷 / 颜色 / 克重*宽度（有米数时再追加米数） / 本卷重量`; they must not replace those facts with opaque range-and-count aggregates such as `01–03 卷 / 本白 / 3 张`. Any manually corrected value is printed from the confirmed review value while the original OCR wording remains audit evidence only; a handle strip whose source omitted both GSM and meters prints the default `65克*5宽` without fabricating `1500米`.

- Raw-material phone capture requires the operator to select `收货入库 / 供应商退货` before photographing or adding pages. That explicit direction is authoritative when the supplier paper uses an ordinary `销货单` title or OCR misses a return marker; OCR may support the choice but must never silently override it. In the currently deployed supplier-return flow, the operator must also select `退给哪家供应商` before capture/recognition because some return notes do not print a supplier name; that selection is the formal return ownership and OCR does not guess or silently replace it. The shared review page then verifies each returned physical item and keeps unit price/amount in the same deployed OCR field disclosure. A selected supplier return stays a signed return-review record and produces no new inbound roll code, label, or inventory.

- Raw-material phone capture must account for the larger files produced by current mobile cameras. Do not reject an otherwise usable delivery-note photo at the old 7.5MB OCR payload threshold or ask the worker to compress it manually. Keep the locally accepted source-file limit separate from the downstream OCR provider's encoded-payload limit, and automatically normalize orientation, resize, and compress an OCR derivative when needed while preserving the source attachment and its audit metadata according to the configured retention policy.

- ERP and the customer ordering mini-program share one upload-size policy: current-camera photos and ordinary photo/PDF evidence accept up to 30MB per source file, general document evidence accepts up to 50MB, and customer print artwork accepts up to 200MB per file. Print artwork explicitly supports `PSD / CDR / AI / PDF / PNG / JPG / JPEG`; it uses the ticket/object-storage upload path rather than Base64 JSON, and the ERP must retain the authoritative file token/attachment ID, byte size, MIME type, digest/scan state, uploader, and bound artwork version. The 7.5MB raw-material figure applies only to an automatically generated OCR binary derivative whose Base64 stays within the provider's 10MB encoded-payload limit; it is never the user-facing source-photo limit.

- The approved raw-material mobile OCR review frame at `screenshots/raw-material-mobile-review-2026-07-20/01-approved-reference.png` is the exact visual source of truth for `核对送货单`. It keeps the real delivery-note image at the top with an explicit full-size view, followed by a concise document-level roll/weight summary and every physical roll in one continuous ledger. A supplier/OCR source line may contain several rolls, but the review ledger must expand it into one visible/editable block per physical roll. Each compact roll block combines its real source-row crop with color swatch, color, specification/width, that roll's independent weight, confirmation state, and edit action; it must not display or edit roll count. - Raw-material OCR review must let the operator remove a falsely recognized physical roll when the original delivery note and actual goods confirm that no such roll exists. The action requires explicit confirmation, immediately reindexes the visible physical-roll ledger, recalculates the confirmed/total count and downstream label count, and remains undoable before final review submission. Removal is an audited human exclusion rather than physical erasure of the OCR source line: retain the original OCR text/evidence plus operator and time, but never generate a roll ID, label, printable row, inventory record, or supplier-reconciliation fact from the excluded false positive. Do not force the operator to fabricate color, specification, or weight merely to get past review.

- Raw-material mobile OCR review keeps the fast path on the all-roll ledger: a physical roll whose required facts are complete exposes a direct one-tap `核对正确` action in its row. `修改` remains a separate secondary action, and only wrong or incomplete facts enter the expanded editor before confirmation; blocked rows use `补全`. Never require a worker to open the editor and then tap a second confirmation merely to accept an already-correct roll.

- Raw-material review PostgreSQL writes use an explicit target-table qualifier for every returned concurrency column. In particular, `UPDATE raw_material_inbounds ...
