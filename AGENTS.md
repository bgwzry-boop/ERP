# Prototype Instructions

Run the local server yourself and open the preview in the in-app browser. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

Before asking the user to restate a business rule, search `AGENTS.md`, `DECISIONS.md`, current product/status documents, implemented server contracts, and relevant tests. Reuse an existing authoritative answer when it is already recorded. Ask only when the answer is genuinely absent, contradictory, or a newly proposed change would alter the established rule; when asking, name the conflict or missing decision instead of repeating a broad discovery question.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Prototype-specific design decisions:

- The selected hybrid redesign at `screenshots/ui-audit-2026-07-11/09-selected-hybrid-redesign.png` is the current visual source of truth for the desktop order-entry and packing/label workbenches. Order entry uses a three-step progress strip, compact pasted-text recognition, editable dense rows, a validation sidebar, and a persistent summary/confirm footer. Packing/label uses top-level `生产任务 / 打包任务 / 打印与设备` tabs, compact priority task cards, packing status filters, and a detail-first view with a fixed task summary plus independently scrolling actions. Print management separates `设备验收 / 上线门禁 / 驱动诊断 / 打印作业`; machine action counts remain visibly separate from qualified output, and onsite execution stays on dedicated mobile role pages.
- Shop-floor execution follows the actual device available to each role rather than assuming every onsite worker has a computer or the same phone workflow. Silk-screen workers, bag-making workers, packers, finished-goods warehouse workers, drivers, and onsite technical/maintenance workers use dedicated phone role pages and do not depend on PC terminals. Raw-material handling is performed by general workers and, when applicable, printing workers through permission-scoped phone scanning/registration; they do not use a PC for that flow. Office desktop workbenches remain the complete dispatch, data-entry, oversight, trusted-printing, and device-administration surfaces, and office A/B can see and coordinate all onsite task queues. Any mobile page must use a dedicated role shell and must not be a desktop left-nav/right-detail layout squeezed into a phone viewport. Platform deployment/ERP operations is not the same role as an onsite technical/maintenance worker and must not imply another factory computer.
- The first production rollout is intentionally raw-material-only. Build the office surface around delivery-note photo/PDF OCR, line-by-line human verification, one scannable label per physical roll, manual label-to-roll verification, and supplier Excel reconciliation at month end. Build the raw-material handler surface as a dedicated scanner/PDA flow that scans one available roll, records the destination machine/area, and moves it to machine-side issue. During this first rollout, raw-material issue must not require or fabricate an order or production-task link; the roll code itself carries color, specification, width, weight, supplier, and inbound traceability so workers no longer hand-copy those facts. Other ERP domains remain hidden in the production frontend through the explicit first-release build flag, while their code remains available for continued development.
- The factory currently has exactly three ERP-capable computers: two office computers assigned to two general office workers, and a third computer used by the owner when onsite for customer statements, finance verification, payment/write-off confirmation, major exceptions, and management. There is no dedicated production-management, warehouse, or finance computer. Future designs must not invent such terminals as a V1 dependency. A production big screen, if added later, is a public read-only display rather than a staff role or approval surface.
- The two office workers are equal-permission generalists and form an A/B backup pair; work is not divided into separate order, inventory, raw-material, statement, or printing roles. Each uses an individual account, both office computers require the complete office feature set and printing capability, and orders, inbound work, printing, statements, and exceptions enter a shared task pool. Their office mobile surface is a focused companion rather than a full desktop replica: it keeps work-order/todo handling and order-exception reminders, and supports the complete raw-material receiving sequence of delivery-note capture, human verification, and printing. Raw-material roll labels must also support trusted direct printing from the office worker's phone so the worker does not have to return to the office computer; mobile print results, device identity, job state, retries, and audit remain server-authoritative. The system records the actual submitter, preserves unfinished state, notes, and next action for handoff, and must prevent silent lost updates through edit occupancy, version checks, or explicit conflict handling when both workers touch the same record.
- The owner uses the third PC for the complete management and finance surface. Owner mobile use should be minimized and is not a V1 dependency; do not mirror the complete owner desktop surface onto a phone by default.
- The owner's mother and aunt are business decision-makers for order priority, production plans, raw-material purchasing, customer-statement review, authorized rounding/write-off decisions, and other operating matters. They cannot operate the desktop ERP, so all of their direct ERP decision functions must be available through dedicated mobile decision-maker pages. Their mobile experience centers on pending decisions, the evidence and business facts needed to decide, approve/return/request-more-information actions, and decision history; it must not expose office data-entry workbenches. When an office worker still enters a decision on their behalf, every delegated entry must separately retain the business decision-maker, authenticated system operator, decision channel, decision time, entry time, decision content, and required evidence or authorization basis. Acting as the data-entry operator never grants the office worker the underlying management approval authority.
- Mobile decision authority is intentionally asymmetric. The owner's mother is the primary operating decision-maker and the aunt is her backup. Either the mother or aunt may decide order priority, production scheduling and insert-order/resequencing requests, customer-statement variances, and authorized rounding. Outbound quantity-variance decisions default to the mother, with the aunt acting as backup unless later narrowed. Major exceptions may be decided only by the owner or the owner's mother; the aunt does not receive that authority. When both mother and aunt are authorized for a scope, the system records the actual single decision-maker for each decision. The first valid terminal decision wins; another client with a stale version is blocked and must refresh rather than overwrite it. Opening an editable decision may create a visible time-bounded occupancy claim; another authorized user may view but cannot silently submit over the active editor, and explicit takeover/reassignment is audited.
- Customer receipt confirmation follows the actual office process. Office A/B may record and settle a payment when the Alipay/WeChat collection notification and the customer's group message or payment screenshot identify the same receipt; the system must retain durable payment-channel/transaction evidence rather than treating the audible speaker alert alone as evidence. If the customer paid less than the receivable, office records the actual receipt but the remaining balance stays open until the owner's mother explicitly approves or rejects rounding. Approval creates a separate rounding decision tied to the statement and payment; office entry does not grant rounding authority. Exact-payment settlement and approved-rounding settlement remain distinct audit cases.
- Raw-material purchasing is planned to move from manual family judgment toward server-generated purchase recommendations. Before the end of each workday, the system produces vendor-grouped recommendations based on authoritative inventory, traced consumption, demand ranges, safety limits, and data sufficiency. The office can review the recommendation, see which supplier purchasing groups should receive each portion, and copy each vendor-specific message with one action for manual distribution. A copied or group-posted recommendation is advisory and is not itself a formal purchase order, inventory write, or supplier commitment; preserve the recommendation inputs, range, confidence, copy/distribution operator, intended supplier groups, and any later human confirmation separately.
- Finished-goods outbound remains a paper-traceable business boundary, but warehouse execution is mobile-enabled rather than paper-only. The office prepares the outbound instruction and trusted paper slip; once the print job succeeds, the corresponding task appears on the finished-goods warehouse phone page. Warehouse staff may open the phone task immediately and begin locating/picking/preparing the goods before the physical paper arrives. Final physical-outbound confirmation remains gated by receiving and checking the current printed outbound slip against the phone task and actual goods; only after specification and quantity match may the warehouse submit outbound. The phone page records prepared/physical-outbound/shortage/mismatch results, paper version/check state, actual executor, and time. The customer, driver, or carrier then receives the goods. The system must distinguish task visibility and preparation, office-created outbound instruction, printed paper version, warehouse physical execution, and final pickup/delivery confirmation.
- Onsite technical/maintenance workers use a phone-only equipment workbench for repair requests, inspection, and preventive maintenance. It should identify the machine, show open repair/inspection tasks, capture fault category, photos, findings, action taken, status, completion time, and actual technician, while office A/B can view and coordinate the same task state. It is separate from ERP deployment and production-environment operations.
- Every worker uses an individual formal account on an individually assigned device; accounts and frontline devices are not shared. Device trust and bounded sessions may reduce repeated password entry, but every write remains attributable to the authenticated employee, and replacing or losing a device requires an explicit revocation/rebinding flow.
- Office mobile raw-material label printing uses Bluetooth to a pre-approved paired label printer. The phone flow must provide label preview, selected printer/device identity, print submission, confirmed result or visible failure, and safe retry without duplicate labels. Printer model/SDK compatibility determines whether this is implemented through a native bridge, vendor SDK, or supported browser capability; the UI must not claim success from a client-side print tap alone.
- The approved high-fidelity order-entry frame at `screenshots/ui-refactor-audit-2026-07-12/09-gpt-order-entry-final-candidate.png` is the exact source of truth for the next order-entry implementation passes. The visible editable table uses one `订单类型` column and must not reintroduce a separate `是否印刷` column; `print`, base-bag style, print color/side, handle color, artwork, and notes remain structured data edited in the selected-row detail area. The initial review state selects row 3 so the custom-print detail and validation flow are visible.
- Order-entry interaction rules are durable: table dropdown arrows stay quiet until row hover, row selection, or keyboard focus; deleting a row requires a danger-styled confirmation; validation items must scroll to and highlight their row; topbar `新建订单` must confirm before discarding unsaved draft content; editing source text after a save immediately marks the draft as requiring re-recognition and must not bypass that confirmation; every editable cell must expose a keyboard focus ring; inventory/review states always retain text such as `缺货60` or `需复核` and never rely on color alone.
- Order-entry examples and future automation must not imply that office staff normally paste multiple unrelated customers into one draft. The common manual case is one customer with multiple order lines or multiple delivery/order groups. Future customer-group automation may recognize many groups concurrently, but each source group/message context must create an independently traceable draft in a queue; concurrent drafts are not merged into one editable order table.
- Batch conversation recognition uses separate queue items: each original source-message order group becomes an editable `order_draft`, while inventory-inquiry chains, temporary holds, duplicate candidates, and unresolved cancellations become line-free intent contexts. Only `order_draft` items may open in the order editor. Every item retains batch/item IDs, request hash, source messages and sequence, and an independent draft ID; changed content under the same batch idempotency key is blocked before any new item is written.
- Operational todo actions must deep-link to their referenced draft, order, inventory item, fulfillment, or statement when the reference can be resolved. Print preview must open the real ERP preview contract, and unknown actions must fail visibly without claiming simulated success.
- Public Todo is an office desktop workbench with count-bearing state shortcuts, page-scoped query/business filters, a dense todo/customer/summary/due/rule/status/reference list, and an independently scrolling detail area. Server sorting, reminder escalation, batch-print trust, reference repair, and deep-link validation remain authoritative.
- A real stock/common-goods WeChat-group example shows that one customer may send several order blocks hours apart, with an inventory question and an office reply between them. Recognition must preserve each source message, sender, timestamp, and conversation order; it must distinguish order lines from inventory inquiries/replies, support one line carrying several color/quantity pairs, and flag likely dimension typos such as `40+30` for confirmation. In this business context `覆膜袋` is a stock/common-goods style, not custom printing. In the confirmed example the later afternoon order block is a new original order even though the customer and date are the same; the system must support that classification rather than silently appending, while fulfillment can still combine eligible orders later. Inventory questions are conditional intent, not confirmed order quantity or inventory reservation, and an out-of-stock candidate may be closed as `库存不足取消` after customer confirmation.
- Customer/group shorthand may concatenate bag color and handle color. Confirmed examples include `焦糖米提 = 焦糖色袋 + 米色提手` and `米白咖提 = 米白色袋 + 咖色提手`; same-color wording such as `安哥拉红安哥拉红提手` means both bag and handle use that color. Recognition should use source-scoped aliases and keep the original wording for traceability.
- Confirmed WeChat stock-order intent rules: a plain `有吗` with quantity becomes `询库存-待客户确认` and does not reserve inventory; only explicit customer intent such as `要 / 留 / 算上` advances it. In an explicit multi-line order, customer cancellation after shortage cancels only the shortage lines by default, while available lines continue unless the customer cancels the whole order. `有的话给我留 N` creates a temporary inventory hold rather than a formal order. Before 19:30 it defaults to same-day 19:30 expiry; at or after 19:30 V1 must require office staff to choose an explicit future expiry and must not silently roll to the next day. An immediate `再加 / 补充` appends to the same draft only before formal confirmation; after confirmation it creates a new original order.
- A standalone cross-draft shortage cancellation is never auto-applied to a historical order. Office staff must explicitly link it to one open, unconfirmed line for the same resolved customer; unknown or mismatched customers fail closed. The target line, source intent and audit log update atomically while the original source draft/message context remains unchanged. Confirmed orders use normal void or new-original-order workflows.
- A shortage-cancelled draft line may be restored only through an explicit server-authoritative command before formal confirmation. Preserve the original cancellation evidence and record reason, authenticated operator, and timestamp; rerun inventory, price, required-field, and low-confidence checks. After formal confirmation, resumed demand creates a new original order and never rewrites the applied cancellation.
- P0 ERP pages use a narrow left navigation rail plus a top page title / action bar.
- The visual density should be high-density SaaS ERP / operational-table style, closer to Jushuitan-like workbenches than large-card dashboards. Avoid oversized cards and large whitespace.
- High density must not degrade into a dated gray legacy-admin aesthetic. The first Gemini desktop order-entry concept at `gemini-desktop-redesign/01-order-entry-desktop-gemini.png` was explicitly rejected as unattractive: too gray, cramped, visually flat, and insufficiently polished. Future concepts should preserve operational density while using stronger hierarchy, refined spacing, modern typography, and a more premium desktop-workbench feel; do not over-constrain the specific palette.
- Use the Picset `studio-genesis` planning workspace as a visual-style reference for future desktop ERP concepts: calm light-gray canvas, refined white rounded work areas, restrained borders, comfortable typography, clear heading hierarchy, consistent control proportions, and polished spacing. Adapt rather than copy it—the ERP still needs denser editable tables and faster scanning. Avoid undersized type and compressed, awkward panel proportions.
- P0 navigation should expose the six usable office pages first and keep later modules as gray placeholders.
- New-user usability is a durable priority across desktop and mobile. Default role surfaces should first answer `我现在要做什么 / 做到哪一步 / 下一步点哪里`: show the current task, a short visible step sequence, one primary next action, and only the supporting facts needed for that decision. Use progressive disclosure for full fields, dense history, and secondary actions, with a clearly labeled `全部功能` or `专业模式` escape for experienced operators. Do not treat visual polish, module navigation, status counts, or a denser table as a substitute for workflow guidance; the accepted raw-material mobile `拍单 -> 核对 -> 打印 -> 贴标` surface is the reference pattern for this clarity.
- Operational copy must earn visible space. Do not repeat the page title, role identity, workflow steps, current status, or next action in explanatory prose. Default screens keep only business facts, blockers, evidence needed for the current decision, and one concise next-action instruction; history, authority detail, environment/source detail, and secondary explanations belong behind progressive disclosure or at the exact confirmation/error boundary where they matter. Prototype `seed`/API/fallback explanations must not occupy normal worker surfaces, and a disabled control should carry a short actionable label instead of a persistent paragraph. New-user guidance is not permission to add always-visible tutorial copy.
- Typography and touch density are role-aware rather than globally scaled. Office desktop workbenches keep 13–14px operational content with 12px table headings and critical statuses; 10–11px is reserved for non-critical metadata only. Decision-maker mobile pages for the owner's mother and aunt use 15–16px explanatory/body text, 16px action labels, and 20–28px headings. Other frontline mobile pages expose no visible business text below 12px and no normal touch control below 44px. Chinese headings use normal letter spacing, and UI weights are limited to 400/500/600/700 for stable rendering across PingFang, Noto Sans CJK, and Microsoft YaHei. Any fixed mobile bottom navigation must reserve safe-area-aware content padding and must never cover the current primary action, including at 320px width.
- Desktop information architecture must balance the former all-in-one crowded workbench with the later under-informative guided mockups. Use first-level navigation for stable business domains, second-level navigation for stable workbenches or state queues within the selected domain, and contextual third-level structure inside the page as workflow steps, tabs, accordions, or the selected-record detail area. Do not add a third persistent sidebar or nest three menu columns. The active page should still expose enough list, status, selected-record, validation, and next-action context for office throughput, while progressively disclosing full fields and secondary operations.
- The accepted layered-density navigation direction has exactly five office first-level business domains: `今日工作`, `订单`, `库存交付`, `对账`, and `更多工作台`. Their stable second-level workbenches are `公共待办`; `订单录入 / 订单池`; `库存查询 / 出库交付`; `对账收款`; and `打包/标签 / 原材料 / 基础资料 / 上线状态`. Wide desktop (`>=1180px`) shows the active first- and second-level locations together in the left navigation; narrow desktop (`768-1179px`, including the required 600px preview) uses an approximately 64px first-level icon rail plus the current domain's second-level strip under the page title with no horizontal menu scrolling; mobile (`<=767px`) never shows the office menu and instead uses a dedicated role shell with role/current task at the top and `当前任务 / 待处理 / 全部功能` at the bottom. Third-level structure stays inside the page as status tabs, workflow steps, detail tabs, or disclosures. Menu changes preserve page-scoped filters, scroll position, and selection; deep links open and select the referenced record; permissions hide unavailable work; counts appear only at the relevant business domain or status tab; unreleased modules sit last and are labeled `后续开放`. Office A/B share the same complete menu and task pool, finance defaults to `对账收款`, and driver/workshop/packing accounts enter their role pages directly.

Desktop keeps the dense domain/workbench/list-detail hierarchy. Each phone role defaults to its current task and short workflow, while `全部功能` exposes only that role's executable actions with task counts; it must never reveal or reproduce the complete office desktop menu.

- Order entry recognition should parse custom-print shorthand into structured bag color, print color, handle color, print side, and notes when possible; examples include `白印黑`, `白袋黑提`, and `黄袋红提`.
- Low-confidence recognized fields must create persisted field-level review evidence. Active pending reviews block normal and split formal-order confirmation on the server; office staff resolves them by explicitly accepting a candidate or editing the related field. Persisted review evidence is authoritative and cannot be bypassed by omitting client fields.
- Confirming an inventory correction is a high-risk write. Before a client invokes the command, it must visibly identify the correction draft, inventory item, system and counted quantities, delta, reason, and that inventory, ledger, todo, and audit projections will change; cancellation must send no write request.
- Confirming a statement write-off is a high-risk financial write. Before a client invokes the command, it must visibly identify the statement, customer, receivable, received amount, variance, handling result, and that settlement/audit records will change; cancellation must send no write request.

Before a client invokes the command, it must visibly identify the task, customer, goods, method, quantity, packages, and that valid reservations may be deducted, a statement candidate may be created, and audit records will change; cancellation must send no write request.

Freeze source inputs and repeat submit during the summary, restore focus on `Escape` or `返回修改`, and fail closed without the matching confirmation marker.
- Production-exception reporting V1 requires the workshop worker to select a fixed reason and explicitly choose `继续生产` or `暂停等确认`; there is no default. Pausing marks only the task as `异常暂停` and blocks daily/final production reporting. Office/management-only resolution requires a note plus final confirmation and has fixed outcomes: resume, pending resequence, wait for material/repair, quantity variance, after-sales/quality handoff, or task void. It atomically updates the task, exception, linked todo, event, and audit log; same-key terminal retries replay the original result, while inventory, reservations, packing, and statements remain unchanged. The desktop exception report, resolution form, and final-confirmation surface stay isolated in `ProductionExceptionPanel` while the workbench retains selection and write orchestration.
- Git-baseline scope review is read-only: it may classify changed files and present ordered review batches, but it must never invoke `git add`, commit, or push. A clean scope only permits manual batch review; it is not evidence that the full worktree is safe to submit or release.
- Missing or unverifiable todo references may be repaired only through an explicit authenticated office action on an unhandled todo. The server must validate the new target, require a reason, atomically persist the new reference plus event and operation log, preserve before/after evidence, and fail closed when the target is invalid; a valid existing reference is never silently rewritten.
- Todo-reference repair must also validate semantic type compatibility. Draft-review todos link only to drafts, print/quantity/carrier todos to fulfillment, statement/payment todos to statements, inventory-correction todos to correction drafts, production todos to production tasks, and shortage/inventory todos only to order lines or inventory items. Candidate lists and editable type controls use the same server-owned allowlist, and visible reference types use Chinese labels rather than internal enums.
- Every newly created todo must pass the same server-owned target resolution and semantic type checks before its business transaction starts. Unsupported, missing, or incompatible targets fail closed instead of relying on later list-time repair.
- Packing completion and its next-step todo are one transaction.
