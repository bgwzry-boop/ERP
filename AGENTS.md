# Prototype Instructions

Run the local server yourself and open the preview in the in-app browser. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Prototype-specific design decisions:

- The selected hybrid redesign at `screenshots/ui-audit-2026-07-11/09-selected-hybrid-redesign.png` is the current visual source of truth for the desktop order-entry and packing/label workbenches. Order entry uses a three-step progress strip, compact pasted-text recognition, editable dense rows, a validation sidebar, and a persistent summary/confirm footer. Packing/label uses top-level `生产任务 / 打包任务 / 打印与设备` tabs, compact priority task cards, and a detail-first production view where machine action counts are visibly separated from qualified output.
- The approved high-fidelity order-entry frame at `screenshots/ui-refactor-audit-2026-07-12/09-gpt-order-entry-final-candidate.png` is the exact source of truth for the next order-entry implementation passes. The visible editable table uses one `订单类型` column and must not reintroduce a separate `是否印刷` column; `print`, base-bag style, print color/side, handle color, artwork, and notes remain structured data edited in the selected-row detail area. The initial review state selects row 3 so the custom-print detail and validation flow are visible.
- Order-entry interaction rules are durable: table dropdown arrows stay quiet until row hover, row selection, or keyboard focus; deleting a row requires a danger-styled confirmation; validation items must scroll to and highlight their row; topbar `新建订单` must confirm before discarding unsaved draft content; every editable cell must expose a keyboard focus ring; inventory/review states always retain text such as `缺货60` or `需复核` and never rely on color alone.
- Order-entry examples and future automation must not imply that office staff normally paste multiple unrelated customers into one draft. The common manual case is one customer with multiple order lines or multiple delivery/order groups. Future customer-group automation may recognize many groups concurrently, but each source group/message context must create an independently traceable draft in a queue; concurrent drafts are not merged into one editable order table.
- Batch conversation recognition uses separate queue items: each original source-message order group becomes an editable `order_draft`, while inventory-inquiry chains, temporary holds, duplicate candidates, and unresolved cancellations become line-free intent contexts. Only `order_draft` items may open in the order editor. Every item retains batch/item IDs, request hash, source messages and sequence, and an independent draft ID; changed content under the same batch idempotency key is blocked before any new item is written.
- Operational todo actions must deep-link to their referenced draft, order, inventory item, fulfillment, or statement when the reference can be resolved. Print preview must open the real ERP preview contract, and unknown actions must fail visibly without claiming simulated success.
- A real stock/common-goods WeChat-group example shows that one customer may send several order blocks hours apart, with an inventory question and an office reply between them. Recognition must preserve each source message, sender, timestamp, and conversation order; it must distinguish order lines from inventory inquiries/replies, support one line carrying several color/quantity pairs, and flag likely dimension typos such as `40+30` for confirmation. In this business context `覆膜袋` is a stock/common-goods style, not custom printing. In the confirmed example the later afternoon order block is a new original order even though the customer and date are the same; the system must support that classification rather than silently appending, while fulfillment can still combine eligible orders later. Inventory questions are conditional intent, not confirmed order quantity or inventory reservation, and an out-of-stock candidate may be closed as `库存不足取消` after customer confirmation.
- Customer/group shorthand may concatenate bag color and handle color. Confirmed examples include `焦糖米提 = 焦糖色袋 + 米色提手` and `米白咖提 = 米白色袋 + 咖色提手`; same-color wording such as `安哥拉红安哥拉红提手` means both bag and handle use that color. Recognition should use source-scoped aliases and keep the original wording for traceability.
- Confirmed WeChat stock-order intent rules: a plain `有吗` with quantity becomes `询库存-待客户确认` and does not reserve inventory; only explicit customer intent such as `要 / 留 / 算上` advances it. In an explicit multi-line order, customer cancellation after shortage cancels only the shortage lines by default, while available lines continue unless the customer cancels the whole order. `有的话给我留 N` creates a temporary inventory hold rather than a formal order. Before 19:30 it defaults to same-day 19:30 expiry; at or after 19:30 V1 must require office staff to choose an explicit future expiry and must not silently roll to the next day. An immediate `再加 / 补充` appends to the same draft only before formal confirmation; after confirmation it creates a new original order.
- A standalone cross-draft shortage cancellation is never auto-applied to a historical order. Office staff must explicitly link it to one open, unconfirmed line for the same resolved customer; unknown or mismatched customers fail closed. The target line, source intent and audit log update atomically while the original source draft/message context remains unchanged. Confirmed orders use normal void or new-original-order workflows.
- A shortage-cancelled draft line may be restored only through an explicit server-authoritative command before formal confirmation. Preserve the original cancellation evidence and record reason, authenticated operator, and timestamp; rerun inventory, price, required-field, and low-confidence checks. After formal confirmation, resumed demand creates a new original order and never rewrites the applied cancellation.
- P0 ERP pages use a narrow left navigation rail plus a top page title / action bar.
- The visual density should be high-density SaaS ERP / operational-table style, closer to Jushuitan-like workbenches than large-card dashboards. Avoid oversized cards and large whitespace.
- P0 navigation should expose the six usable office pages first and keep later modules as gray placeholders.
- V1 role tools that are already implemented must appear after the six P0 office pages in a permission-scoped secondary navigation group; internal enum values such as `pickup`, `delivery`, and `express_ltl` must be converted to Chinese labels at the API/UI boundary and must not appear in visible operational tables.
- Employee/machine maintenance must show the same server-authoritative eight-role formal-account readiness used by release gates. Show aggregate role coverage and blocker labels only; seed accounts never count, and permission/API failure must clear the projection rather than preserve a prior management view.
- Employee/machine maintenance defaults to formal imported accounts. Seed employees are isolated behind an explicitly labeled demonstration view and never replace the formal empty state or count toward readiness.
- Employee workshop/machine assignment is manually editable after formal employee import. V1 supports `固定机台` (workshop + machine), `杂工 / 流动` (workshop only), and `暂未分配`; the initial default map is workshop 1 = machines 1-3, workshop 2 = machines 4-6, workshop 3 = machines 7-9, but authorized staff may change it with operator/time/reason audit. Employee import must not be blocked by blank workshop/machine fields, while workshop-role account readiness still requires a default machine.
- Order entry uses a large pasted-text input above editable parsed table rows. Common fields edit inline; complex print details open in a side panel.
- Order entry recognition should parse custom-print shorthand into structured bag color, print color, handle color, print side, and notes when possible; examples include `白印黑`, `白袋黑提`, and `黄袋红提`.
- Low-confidence recognized fields must create persisted field-level review evidence. Active pending reviews block normal and split formal-order confirmation on the server; office staff resolves them by explicitly accepting a candidate or editing the related field. Persisted review evidence is authoritative and cannot be bypassed by omitting client fields.
- Confirming a production-ready custom-print order must create its production task and fulfillment placeholder in the same order-confirmation transaction; new custom orders must not depend on API-startup seed-task synthesis before they can enter production, packing, trusted printing, and fulfillment.
- In order-entry tables, custom printed orders should not appear as plain `空白袋` in the visible style/type column. Show the visible type as `定制印刷` while keeping the base bag / inventory style such as `空白袋` available in detail data for stock and production matching.
- In outbound / fulfillment lists and labels, custom product specs should use factory shorthand. Show product name + size + compact color spec + print side + quantity + notes; compact color spec uses bag color plus print color such as `白印黑`, and bag color plus handle color such as `白袋黑提`. If both apply, show both, e.g. `白印黑 / 白袋黑提`.
- Bag-making machine counter values, including the Ounuo machine's built-in daily report, are machine action/cycle counts, not finished-goods output. Prototype UI should label them as machine count / cycle count, never as qualified finished quantity, inventory, fulfillment quantity, or chargeable quantity.
- Inventory status colors are consistent: available green, reserved / occupied yellow, out-of-stock red, pending-handling gray.
- Statement / payment pages are customer-first: customer list on the left and the selected customer's statement-period orders and payment status on the right.
- Shared state colors are consistent across modules: normal blue / green, pending yellow, exception red, completed muted green, voided gray.
- Raw-material inbound should follow the real shop-floor sequence: raw-material supplier delivery/sales note photo from the goods-receiving moment, OCR prefill, customer-service / office review, one label per roll or piece, label printing, physical label attachment to the matching roll, then phone scan / signed-note upload before the roll becomes available inventory. This raw-material delivery note is unrelated to finished-goods outbound / customer delivery notes. Numbering has two layers: supplier document number is optional and recorded only when present; ERP inbound ID and roll/piece IDs are mandatory internal identifiers for search, labels, inventory, issuing, and cost traceability.
- Raw-material machine-side issue in V1 creates issue traceability and moves material to machine-side status after label attachment, but it must not create finished-goods output, treat machine counts as qualified quantity, or allocate order cost / margin. V1 now allows full-roll/full-piece issue plus a narrow split-roll partial issue path for weighted rolls: the source roll keeps remaining available weight, the machine-side child roll gets a `RMI-SPLIT-*` trace, and the issue record keeps source/child linkage. V1 also allows full consumption, measured partial machine-side consumption with remaining weight kept at machine side, machine-side leftover return to `余料待复核`, and warehouse/packing review of returned leftovers back to `可用`. These remain traceability / inventory-state actions only. Production-task precise matching, cost allocation, loss calibration, and margin allocation still require later workflows.

Requirements refinement cadence:

- Do not ask one-by-one questions for low-level implementation details.
- Batch small implementation details into reasonable default rules and document them.
- When small open questions remain, present several at once in a concise "question + recommendation + reason" format so the user can approve, reject, or supplement them in batches.
- Ask the user only for decisions that materially affect business process, permissions, pricing, inventory, reconciliation, customer communication, responsibility tracking, or operator workload.
- When proposing grouped defaults, keep examples concrete and business-specific.
- After documenting accepted requirement answers, automatically continue with the next grouped question set unless the user explicitly asks to pause or stop.
