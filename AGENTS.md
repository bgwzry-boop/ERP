# Prototype Instructions

Run the local server yourself and open the preview in the in-app browser. Do not give the user server-start instructions when you can run it.

All ERP environments have one controlled deployment line independent of Codex conversations. A task may edit only its own branch/worktree; it must never deploy from the shared dirty working tree or treat an in-app preview as a release. Review Sites, staging, and Tencent production deployments must each use a clean, fully pushed, immutable 40-character Git commit and a verified `erp-controlled-release-lock-v1` for the exact target. The same lock identity must be embedded in the frontend and API, and deployment is complete only after the target reports the same commit, target, version, and lock digest. Only an explicit integration/release task may assemble changes from several conversations and promote them; ordinary modification tasks do not deploy, repoint production, or create a second “current version”.

Staging has one canonical Git baseline: the remote branch `codex/staging-current` must point at the exact immutable commit currently reported by both the staging frontend and `/api/health`. A staging release is incomplete until that non-force-updated branch matches the deployed commit. New modification work fetches and starts from this baseline; a conversation-specific deployment branch is evidence/history, never a second current version. Local `4174` always declares and visibly marks itself as `本地修改稿 · 未部署`, including its base commit and dirty state, and must never be described or shown as the deployed server version. After a successful release, the owner-facing browser is opened on the staging URL with the verified release commit as a cache-busting query; do not leave `4174` open as if it were the released result.

Local port `4174` is permanently reserved for the complete desktop review app at `docs/prototypes/raw-material-roll-inventory-review`, whose application identity is `bagwin-complete-review-4174`. The root ERP workbench uses `5173` and must refuse to start on `4174`; the complete review app must refuse any other port. Start the accepted review through the root `npm run review:dev`, and verify it with `npm run review:check` before showing it. A URL or HTTP 200 alone is not identity evidence: delivery must verify the app-id marker, complete business navigation, desktop shell and API health. If the process behind a local origin changes, use a fresh cache-busting URL or reload; both development apps also poll their served HTML identity and reload themselves when that identity changes, so a still-running old document cannot silently masquerade as the new server.

The `4174` review entry must also isolate viewport families. If an already-mounted phone flow crosses into desktop width (or a desktop flow crosses into phone width), the document must reload through the canonical complete-review entry instead of allowing the root mobile application to expand into its legacy desktop shell. The phone raw-material flow remains available at phone width, but its historical desktop navigation is never an accepted `4174` desktop review surface and must not appear merely because an in-app pane or browser window was resized.

Bare local navigation to the root `5173` workbench is never an accepted review entry and must redirect to the verified `4174` complete review app. The internal root workbench is reachable only through the explicit developer marker `?internalWorkbench=1`; never show that internal URL to the owner as an ERP preview. Browser delivery uses a fresh `4174` URL only after `npm run review:check` passes.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

Before asking the user to restate a business rule, search `AGENTS.md`, `DECISIONS.md`, current product/status documents, implemented server contracts, and relevant tests. Reuse an existing authoritative answer when it is already recorded. Ask only when the answer is genuinely absent, contradictory, or a newly proposed change would alter the established rule; when asking, name the conflict or missing decision instead of repeating a broad discovery question.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Prototype-specific design decisions:

- The public staging/review URL uses one passwordless but still authenticated test identity on both desktop and mobile. The review shell must explicitly exchange that fixed preview identity for a backend-signed seed session; it must not expose the account/password screen, fabricate a client-only identity, or remove operator attribution. This exception is limited to the review wrapper and test data. Formal production entry keeps runtime account authentication. A served review document also compares its embedded release commit with uncached origin HTML and reloads when the controlled release changes, so a phone restored from an old browser page cannot silently return to a stale login flow.

- 原材料手机拍单默认按一页保持轻量，但拍完第一页后必须提供明确的“没有第二页，开始识别 / 还有第二页，继续拍”分支；同一张厂家送货单最多按顺序附加 4 页并作为一个入库草稿、一个单号和一组汇总一起识别复核，不能把少见的两页单据默认为两张独立单据，也不能事后仅凭供应商或单号自动合并已经建立的草稿。每页原图分别作为不可替代的审计附件保存，OCR 表格和每条明细保留 `sourcePageIndex`，手机逐行核对与放大原图必须切到该行真实来源页。分页页小计不得冒充全单汇总；整单明细、总重量和声明金额不一致时继续显式阻断人工复核。厂家表头的 `编号 / 商品全名` 出现 `57 / 号 / 空白` 等轻微 OCR 漂移时，只要 `规格 / 单位 / 数量 / 单价 / 金额` 的业务列仍完整，就按厂家逐卷版式恢复解析，禁止因首列表头漂移而丢弃整页。
- 原材料手机拍单选择或拍摄页面后，必须立即显示按顺序排列的逐页缩略预览、明确页码，并允许在开始识别前查看大图或删除单页；预览使用 OCR 副本以控制手机内存，正式审计仍保存每页未经替代的原图。同一张单有多页时，界面需明确提醒全部添加后再识别，不能只用“已拍 N 页”的文字替代视觉核对。
- 原材料颜色必须同时保留“厂家票面颜色”和“厂内标准色”，不能假设不同供应商对同一实物使用相同叫法。后台按供应商维护可修改、可停用且有操作审计的 `厂家票面颜色 → 厂内标准色` 映射；OCR 先保留票面原文，再按当前供应商规则优先换算，之后才允许使用全厂通用别名。未匹配或同一厂家规则冲突时必须阻断并人工选择厂内标准色；一次人工核对不得静默学习或改写映射，只有有权限的后台维护动作才能更新规则。
- 工厂标准色的首批权威来源是【下单小程序】中已提交的横款/竖款袋子实拍：图片文件名与结构化袋身/提手字段共同确认单一布料颜色。`焦糖米提 / 白黑提 / 粉袋酒红提` 等是成品配色组合，必须拆成袋身色和提手色，组合名本身不得进入卷料标准色。当前首批为 `shared/factoryStandardColors.js` 中 35 个有实拍证据的标准色；工厂已明确确认不存在 `云雅绿 / 天池蓝 / 梦幻紫`，任何色卡、导入、OCR 或映射都不得把它们作为厂内标准色或普通候选色。历史 `本白 / 大红 / 宝兰 / 天兰 / 桔红` 作为明确兼容别名分别归一到 `白色 / 红色 / 宝蓝 / 天蓝 / 橘色`，新厂家叫法仍必须走有审计的供应商专属映射，不能凭相似颜色静默合并。
- 原材料手机 OCR 复核不得再用固定厂内颜色下拉框要求逐卷手选。已命中厂家规则时直接显示 `厂家票面颜色 → 厂内标准色` 自动换算结果；首次新叫法或规则冲突进入一次性的有权限规则维护，允许从已有厂内标准色选择或显式新建标准色，保存后立即回填当前单据中同一票面颜色，并供以后同厂家自动换算。
- 原材料手机 OCR 核对页的返回不能只是退出页面并遗留后台草稿。对仍处于 `已识别待复核` 的单据，必须明确提供 `放弃这张，重新拍 / 继续核对 / 保留草稿，返回首页`：放弃复用有权限且有审计的作废动作，服务端确认 `已作废` 后才返回拍单首页；已作废草稿不进入正常入库、手机未完成、搜索、统计或供应商对账列表，也不形成库存、应付或对账数据，但原图、作废人、时间和原因继续保留用于审计。

- The desktop review topbar begins directly with global search. Do not place a fixed factory-name label such as `虎门工厂` between the sidebar brand and search: the brand and current workbench already establish context, while the repeated label wastes scan space. If multi-factory switching becomes real later, introduce an explicit permissioned factory selector rather than restoring static text.

- ERP 品牌位采用两套专用矢量素材：登录与首次改密页使用经过光学校准的完整横标，页面显示约 `250 × 82 px`，下一行保持 `河北禄兴包装制品有限公司 · ERP 生产系统`；系统内页左侧导航栏顶部使用原完整横标，品牌栏固定 `58 px` 并与右侧顶栏严格齐平。桌面宽侧栏显示完整横标，折叠或紧凑侧栏仅显示独立 W 图形标，禁止压缩完整横标或再次拼接界面文字。

- Desktop `原料管理 → 卷料库存` is scanned and paged by authoritative numeric width, not by the roll trace code or incidental API order. The first list column is `规格（宽幅）`: width is the primary value and the complete material specification is secondary; numeric widths sort ascending and missing/unconfirmed widths remain last. The width filter and available-stock distribution reuse the same dynamic width order. The stable roll code remains a searchable/scannable trace key, appears compactly in the final list column with the full value retained in detail, labels and tooltips, and must never be renumbered merely to change presentation order. New OCR rolls keep the canonical `RM-<inbound identity>-<two-digit physical-roll sequence>` rule, while historical/manual and split-roll identifiers remain compatible so existing barcode and traceability relationships are not broken.
- Desktop `原料管理 → 卷料库存` contains only real warehouse states: exact `可用`, actual machine-side issue/consumption, and explicit roll-level `inventoryStatus = 余料待复核`. A newly recognized receipt whose inbound status is `已识别待复核` or whose roll label is merely `待人工复核` remains only in `收货录入`; it must never be reclassified as leftover inventory or appear in the physical-roll ledger before review completes.

- Desktop `基础资料 → 员工机台` uses the main list for operational scanning only: `序号 / 员工 / 岗位 / 车间 / 机台 / 状态`. `序号` is the stable one-based position in the current authoritative employee roster and stays narrow; the employee name remains the primary row identity and the selected-detail title. The login `账号` does not occupy a repeated list column; it appears in the selected employee's right-side detail together with the employee number and remains searchable as hidden metadata. Account lifecycle actions continue to use the server-authoritative employee-account flow.

- ERP account and permission rollout follows Taobao-style subaccounts. The owner resumed implementation on 2026-08-25: an authorized `permission.manage` administrator can create a distinct subaccount, optionally bind it to one employee, assign one or more reviewed role bundles, and apply audited per-permission allow/deny exceptions. New subaccounts remain login-disabled until a separate one-time temporary-password action; suspension, reactivation and permanent disablement invalidate existing sessions, optimistic permission revisions prevent stale overwrites, and the temporary password must never persist in or reappear from the user list. Employee profile, operational role, workshop/machine assignment and payroll position remain separate facts; creating or importing an employee must never automatically create an account, enable login, or infer permissions from payroll/role labels. The current implementation governs functional permissions only; do not present workshop/customer/warehouse row-level data scope as enforced until each underlying read/write query consumes a server-authoritative scope contract. The capability does not authorize bulk creation or enablement: real accounts are created only through an explicit administrator action for an accepted person.
- The owner explicitly rejected a technical permission-table UI as too difficult to understand. The default administrator experience under `基础资料 → 员工机台 → 岗位分配` is person-first and position-first: select the subaccount, click one or more visual position cards such as `办公室 / 库房 / 财务 / 司机 / 车间 / 打包`, review short written business scopes, and save. The server still derives and audits the exact permission bundles and preserves any existing allow/deny exceptions, but raw permission keys and per-key dropdowns stay out of the everyday position-assignment flow.

- Desktop `基础资料 → 员工机台` selected detail groups personnel information as `员工档案 / 工作安排 / 账号信息`. `员工档案` includes employee number, name, age, entry date, factory tenure, and employment status; `工作安排` includes role, workshop, current machine, and notes. Age is derived from the maintained birth date and factory tenure is derived from the maintained entry date, so neither drifting value is stored or invented. Missing dates display `未维护 / 待维护入职日期`; future payroll seniority-award calculation must reuse this same authoritative entry date and tenure rule rather than introducing a second manual seniority value.

- Attendance and payroll link through the stable ERP employee number, never through a mutable name. Deli, Enterprise WeChat, or a replacement attendance provider keeps its person identifier as an external identity mapping; immutable raw punch events resolve through that mapping to the ERP employee, reviewed minute-level work segments, and the employee/month payroll draft. `员工机台` may show a compact attendance/payroll entry point, while accountant-wide calculation and review live in the independent `财务管理 → 工资核算` workbench. The employee phone `我的考勤` view exposes only that logged-in employee's punch timestamps, daily hours, current-month confirmed hours, attendance exceptions, and `截至今日` estimated pay. Employees cannot see coworkers or edit raw punches; they may submit an explanation for HR review. Running estimates must state that unresolved attendance is excluded and that the amount is not final payroll.

- Basic wage is defined by payroll position, not repeated on every employee. A stable `payrollPositionKey` is independent from permission role, workshop and machine assignment; each employee links to one effective payroll position, while the versioned payroll policy owns that position's explicit calculation mode, rate composition and effective period. Hourly positions use base hourly wage plus hourly position allowance; the supplied driver position uses a separate daily wage and must never be coerced into an invented hourly rate. A payroll draft snapshots the resolved position/rate version for audit. Performance awards, leave deductions and other employee-specific adjustments remain line-level accountant actions with written basis and evidence; they never become a hidden personal base wage. Until the formal position-rate contract and approved values are deployed, current per-employee wage fields are legacy intake data only and must not be represented as the final wage authority.

- The currently enabled single employee account is the accepted functional pilot scope for employee self-service, attendance visibility and payroll permission testing. The other active accounts stay pending administrator review until the owner supplies and accepts their personnel data. A one-person pilot never satisfies formal whole-factory payroll readiness and must not be reported as production attendance/payroll acceptance.
- The owner-provided workbook `26年工资 (2).xlsx` is the current payroll-business source for position names and wage composition. It contains 28 employee sheets plus `汇总`; hourly payroll rows use `工时 ×（基本工资（时薪）＋岗位补贴（工时））＋综合绩效＋工龄奖`, while `送货司机` uses a daily-wage field. Current recurring examples include `制袋机-理袋女工 10+5 元/小时`, `印刷机-男工 15+5`, `普工-男杂工 15+3`, `普工组长 15+5`, `库管-女 10+5`, `办公室-女 10+2`, `女杂工 10+2`, `提手-拿袋 10+2`, `技术工 15+5`, and `送货司机 180 元/天`. The workbook's seniority rule is `满1年 30元/月，之后每多1年增加15元` through at least eight years. Preserve the original job wording and separate hourly/daily calculation modes; do not replace these supplied values with invented role-level examples. Before publication, finance must still confirm the exact effective date and any temporary/early-period exceptions already visible in the workbook.

- Production environment preflight treats attendance/payroll integration as an explicit staged gate. The current punch machine is not assumed to expose a usable API, so `ERP_ATTENDANCE_PROVIDER_MODE` remains absent or explicitly disabled during the one-person functional pilot; this is a visible non-blocking warning for the approved raw-material-first rollout, while formal payroll readiness stays blocked. The existing verified `http_json + deli` adapter may be enabled only if real Deli authorization is later confirmed. A replacement punch machine/provider must receive its own stable provider key and tested adapter while preserving HTTPS, non-placeholder credentials, positive timeout, PostgreSQL payroll storage, read-only precheck, immutable raw events and stable employee mapping; never relabel a replacement as `deli` or fall back to name matching. The full production real-value intake includes this group under `技术/财务/管理`, but the raw-material first-release minimum blocking fragment excludes it. Passing env preflight never substitutes for a read-only live sync precheck, stable employee mapping, a persisted closed-month full-coverage import, or payroll field acceptance.
- A newly configured attendance provider is checked through the server-side read-only sync precheck before the first formal import. The precheck may call the configured gateway for an explicit time range, but it writes no batch or punch data and returns only aggregate validity, duplicate, mapping-coverage and already-imported/new counts. It never returns ERP employee identities, provider person IDs, punch IDs, raw payloads or tokens. The actual write endpoint fetches and assesses the source again; any invalid or out-of-range timestamp/date, duplicate punch identifier, unmatched/ambiguous mapping, or incomplete active-employee mapping aborts the whole import before a batch or punch is persisted. Precheck success does not satisfy payroll readiness.

- Payroll performance awards, leave/absence deductions, and other deductions are explicit accountant-entered values on a `工资草稿`; they are never inferred from an after-sales clue or silently applied to pay. Every amount-changing adjustment requires a written basis plus at least one authenticated business-owned image/PDF attachment and saves immutable before/after values, evidence IDs, operator, and time. Only `draft` lines may change; after accountant review, any correction requires a newly generated payroll revision. Employee history follows the stable ERP employee number even after departure, while CSV export is bound to one exact payroll-run revision and carries a server-generated SHA-256 digest. These code capabilities do not authorize production payroll until the real attendance endpoint, employee-to-payroll-position links, approved position-rate policy values, permissions, database migration, and acceptance evidence are configured.
- Payroll draft creation and status changes are optimistic, database-enforced accounting transitions. A new draft revision is accepted only when it immediately follows the persisted latest revision for that payroll month; concurrent requests converge on one row and all stale attempts return an explicit conflict. Manual line adjustments compare the persisted prior performance/leave/other values before updating, so concurrent edits cannot silently overwrite one another. Review, lock and payment are exact forward transitions `draft → reviewed → locked → paid`; they never rewrite payroll lines, and the first persisted reviewer/locker/payer, timestamps and payment reference cannot be replaced by a stale request. PostgreSQL guards keep run identity/generation evidence immutable and allow line insert/update/delete only while the parent run is `draft`.
- Formal payroll CSV export is a sensitive write-like action, not an ordinary payroll preview. Only finance/management accounts with the explicit `payroll.export` permission may export, and only a `reviewed / locked / paid` run may produce a formal file. Every successful export writes an immutable digest-only audit event containing the exact run/revision/status, safe filename, SHA-256 content digest, row count, operator and server time; it never duplicates wage rows in the audit table. The insert compares the current persisted run snapshot, so a concurrent state transition yields `PAYROLL_EXPORT_SNAPSHOT_CONFLICT` rather than recording ambiguous evidence. Draft exports remain blocked.
- Attendance-day rejection means `暂不计薪`, not `待复核`. A rejected anomaly keeps the original immutable punch evidence and raw paired minutes for audit, resolves the pending-review blocker, and forces the confirmed/payroll work minutes for that day to exactly zero. It must never silently restore raw minutes or remain permanently pending after an authorized review.
- Payroll-policy input fails closed instead of repairing questionable finance rules silently. Standard daily minutes and overtime multiplier must be valid explicit numbers; every seniority-award tier requires a unique integer service-year threshold and a bounded nonnegative monthly amount. Every payroll-position rate requires a unique stable key, written position name and explicit `hourly / daily` calculation mode: hourly mode requires a positive base hourly wage and bounded nonnegative hourly position allowance; daily mode requires a positive daily wage and rejects hourly-rate fields. The authenticated server operator and server clock own creator/reviewer/time evidence, regardless of client fields. A new version must first persist as `draft`; the same returned version id may then publish, while a first request that tries to create `published` fails with `PAYROLL_POLICY_DRAFT_REQUIRED`. A published or retired policy version is immutable in both local and PostgreSQL paths; a changed rule always receives a new version and integrity digest, and the same effective date cannot publish twice.

- Formal payroll readiness is a non-mutating, fail-closed server check for one selected payroll month. Payroll follows the China factory natural month: a formal draft may be generated only after that month ends, normally during the following month's `1–5` review window. Readiness requires PostgreSQL persistence, a configured real attendance source, at least one active employee, complete profile dates, complete employee-to-payroll-position and attendance mappings, one matching rate for every used position in the published month-effective payroll policy, and one or more successful zero-unmatched import ranges whose clipped union continuously covers the exact factory-local interval from the selected month's first day `00:00 +08:00` to the next month's first day `00:00 +08:00`. It also requires zero pending attendance reviews and enabled employee self-service accounts that have completed their mandatory password change. The projection returns counts and criterion states only; it never exposes employee identities, attendance tokens, or connection strings. Every human operational role may read only its own attendance, while coworker attendance and payroll workbenches remain finance/management permissions. A successful read-only precheck, a partial-month import, a future-ended request made before period close, an import from another month or the one-person pilot never authorizes a formal payroll draft. Draft generation additionally requires every employee in the run to have at least one confirmed attendance day in the selected month; an employee with no linked punch cannot receive an estimated seniority award or a zero-hour payroll line and instead remains explicitly blocked for attendance review.
- `attendancePayrollRepository` is a first-class production persistence store and must remain in the system V1 persistence catalog alongside the other finance repositories. Production readiness must fail closed unless it reports `postgres`; a payroll-specific readiness check may not substitute for the system-wide repository inventory, and adding another formal repository requires updating both the persistence option profile and the system catalog so their counts cannot drift.
- Database migration and restore validation explicitly require the eight formal attendance/payroll tables (`attendance_import_batches`, `attendance_punches`, `attendance_day_reviews`, `payroll_policy_versions`, `payroll_runs`, `payroll_lines`, `payroll_line_adjustments`, `payroll_export_events`) plus the employee birth/hire/payroll-position/attendance-identity columns. A generic schema-table count is insufficient: losing any one of those tables or employee columns must fail the migration or restore check. Legacy employee wage columns may remain during migration but cannot substitute for the payroll-position rate policy. The first read-only source check still restores schema and migration metadata only; real scheduled/offsite business-data backup and recovery evidence remains a separate production requirement.

- The versioned `员工机台` import is the batch intake path for formal employee profile/payroll/attendance setup. It keys rows only by the stable ERP employee number and supports birth date, hire date, stable payroll-position key, normalized attendance provider key, and provider-owned external person ID. Position rates are maintained once in the versioned payroll policy, not copied into every employee row. `deli` remains the stable key only for the existing Deli adapter; a replacement provider receives a new key. Duplicate provider/person mappings fail in precheck, execution payload, transaction writer, and PostgreSQL uniqueness. Blank optional profile cells preserve existing formal values on re-import; clearing or unbinding is a separate single-employee audited action. Re-import must never disable an enabled account or reset account/profile review state, and departed/merged records cannot enter the active payroll-profile batch.

- Desktop finished-goods inventory replaces the derived normal `状态` column with one exact inventory-allocation view. Keep `在库` as an exact count; the shared `库存结构` component shows exact `可用 / 占用 / 锁定 / 待处理` quantities, the rounded available percentage, and a thin semantic segmented bar in both the list and selected detail. Ordinary derived labels such as `可用 / 已占用 / 待提货锁定` do not occupy a separate column because they repeat the quantities and can falsely imply that an entire stock row is unavailable. Only action-driving exceptions such as `冻结 / 盘点差异 / 待复核 / 缺货 / 待处理` remain visible as written labels; colour never replaces the text or exact quantity.
- Finished-goods inventory reuses the raw-material roll-inventory colour language instead of rendering bag colour as plain text. Every concrete finished-goods colour is shown as the same square factory-colour swatch plus the written colour name in the inventory row, selected-detail heading, and `袋身 / 提手` fact. The swatch is a shared component and colour map consumed by both roll inventory and finished-goods inventory; it never replaces the written label. The Miniapp-photo-derived names in `shared/factoryStandardColors.js` are the canonical factory tokens; historical `大红 / 宝兰 / 本白 / 天兰 / 桔红` remain input aliases rather than separate swatch identities. `米白` retains its explicit swatch, while a future laminated colour such as `金色` requires its own accepted photo/master-data evidence before becoming a standard colour.
- Desktop finished-goods inventory pages (`无纺布袋库存 / 覆膜袋库存`) do not repeat generic names such as `纯色通货袋 / 印刷通货袋` beside the shared `纯色通货 / 印刷通货` tag. The first list column is `通货类型` and contains only the shared business-type `SemanticTag`. The selected-detail heading uses the concrete `规格 + 颜色`; the business facts contain the type tag once, and `图案` appears only for printed common goods rather than showing a meaningless `—` for pure common goods. Apply this consistently to both inventory categories.
- In desktop `成品资料`, generic names such as `纯色空白袋 / 印刷通货袋` duplicate the shared `纯色通货 / 印刷通货` type labels. The first list column contains only the finished-goods category, and the `通货类型` column contains only the shared business-type `SemanticTag`.
